# Controller-engineered task — template

Use the selected experimental route only after its map, validation and execution bindings are supported. This template supplies mechanical section names, not semantic planning approval or owner authority. Place uniquely named original-outcome sections under Original requirements; use the same owning runner definition for entries, source anchors and proof selectors. Do not duplicate requirement prose in a second inventory.

## Original requirements

Original issue, accepted decisions and observable outcomes, each with a unique section heading and retained original source binding.

## Engineering decisions

Settled behavior, architecture, interfaces, ownership/failure contracts and relevant source discovery. Ordinary local coding choices stay with implementors.

## Source boundaries

Original integration baseline, task branch, bounded paths, dependency/provisioning prerequisites and applicable authorization/profile controls.

## Proof and sequencing

Distinguishing cases and required artifacts/measurements, targeted development/correction checks and risk-selected acceptance checks. Name assignment bases, plan/predecessor review and due proof; retain future obligations and accepted owner. Planned advancement is not rejected-candidate rework. Final review covers the combined original-baseline diff.

## Closeout

Fresh independent plan and implementation review, separate controller approval, exact-candidate protected qualification/integration and installed verification before closure and safe owned-ref cleanup.
