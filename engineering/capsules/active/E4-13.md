# E4-13 — Restrict default Food form to conventional Nutrition Facts fields

## Goal

Reduce ordinary manual Food-entry density so a new Food exposes only the familiar conventional Nutrition Facts nutrient set by default, without altering the canonical nutrient model, persistence semantics, unknown-versus-zero behavior, or existing extended nutrient data.

## Outcome

New Food shows the accepted fifteen conventional Nutrition Facts nutrient fields after serving information in a deterministic familiar order. Extended canonical nutrients are not rendered on the default New Food surface, but they remain in the existing form/payload model as unknown rather than zero. Editing an existing Food continues to show any populated extended nutrients without data loss.

## Non-goals

- No grouped `More nutrients` or `Add nutrient` redesign; E4-14 / #127 owns that work.
- No canonical nutrient ID, unit, hierarchy, catalog, or display-order change.
- No Food API or mutation contract change.
- No nutrient status-model change.
- No backend, runtime, SQLite, or migration work.
- No OCR parser, OCR confirmation, USDA mapper, or USDA import redesign.
- No regulatory-label authoring or certification behavior.
- No inference that an absent field means zero.
- No conversion of `not a significant source` text into literal zero.
- No unrelated Food-form layout or serving-editor redesign.

## Background

The canonical nutrient catalog has grown beyond the field set appropriate for ordinary manual Food entry. The current New Food screen passes the complete sorted canonical nutrient-definition collection both to `useFoodForm` and directly to `NutrientEntryList`, so every canonical nutrient is rendered for a new Food.

The existing form model is already semantically correct for E4-13. `useFoodForm` merges every supplied canonical nutrient definition into the form state, initializes absent nutrients as `amount = null` plus `data_status = unknown`, and builds create/update payloads over that full merged collection. `NutrientEntryList` already derives blank input as unknown and an explicit numeric zero as `zero`.

Edit behavior is also already partly aligned: `FoodFormScreen` sets `hideUnknownByDefault` for saved Foods, allowing populated extended nutrients to remain visible while absent unknown fields stay out of the ordinary edit surface.

E4-13 therefore narrows only the New Food presentation definitions. The complete canonical definition collection must continue to initialize `useFoodForm`, preserving hidden extended unknown entries and the existing payload authority.
