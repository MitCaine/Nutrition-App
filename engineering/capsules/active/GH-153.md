# GH-153 — Validate remaining supported remote API responses

## Goal

Complete deterministic runtime validation for the supported mobile remote API
response surface that remains outside the bounded high-risk validation completed
by GH-139.

## Outcome

Every supported remote response family selected during discovery fails closed at
its capability API boundary when a successful HTTP response violates the
canonical backend response contract.

Valid canonical responses preserve their current application types and behavior.

The generic `apiRequest` transport remains domain-agnostic.

## Non-goals

- No generic response-validation framework inside `apiRequest`.
- No backend contract redesign.
- No API-version change.
- No local SQLite runtime change.
- No synchronization, fallback, dual write, shadow write, or cross-authority
  cache.
- No UI or navigation redesign.
- No speculative validator for an unsupported or unproven response shape.
- No unrelated code simplification.

## Background

The pre-2.0 audit identified the remaining remote response surface as the only
material runtime-contract cleanup before release.

GH-139 validated the highest-risk Daily Log, History, Complete, Daily Summary,
and Recipe publication response families. Its explicit exclusions include
Recent Entries, edit context, Recipe duplication, Recipe nutrition, Foods,
Targets, OCR, USDA, and Calendar.

Current generic transport still returns successful JSON through a compile-time
TypeScript assertion.

  `c3b53b9825236fc13b4cad2af1b0f8de6018af55edde98f72526ee9a633754b6`.
- The 28 validation-required operations are exactly: Calendar 4, Foods 12,
  residual Logging 2, OCR confirmation 1, residual Recipes 6, and USDA 3.
- The 14 already-qualified operations are exactly: eight GH-139 Logging
  operations, OCR parse, Recipe publication, and all four Target operations.
  These remain read-only regression authority for GH-153.
- `deleteLog` and `deleteRecipe` are intentional HTTP 204 operations and require
  no response-body schema.
- GH-153 remains one GitHub issue and one lifecycle capsule with four bounded
  implementation packages. Child issues are not justified by the current
  authority.
- GH-153-A owns Calendar plus residual Logging contracts: four Calendar
  responses, Recent Entries, and Daily Log edit context.
- Daily Log edit context has an intentional compatibility representation:
  backend routing uses `response_model=None` and omits five nullable current
  authority fields when they are absent. The mobile validator must preserve
  that proven wire form rather than making those omitted fields unconditionally
  required.
- GH-153-B owns the Food core contract family and will replace the current
  shallow Food source-only check with complete canonical Food response
  validation. It also covers nutrient catalog, Food lists/recent/resolved
  nutrition, delete results, and Food-returning mutations.
- GH-153-C owns USDA search/preview/import and OCR confirmation. It depends on
  GH-153-B so USDA import and OCR confirmation reuse one canonical Food parser
  rather than defining competing Food authorities.
- GH-153-D owns residual Recipe list/get/create/update/duplicate and nutrition
  response validation. Existing GH-139 Recipe publication validation remains
  authoritative and unchanged.
- Capability-local schemas remain the selected pattern. No generic global
  response-validation framework will be introduced.
- Existing remote error mapping remains the selected failure boundary.
  Malformed successful reads must become non-retryable invalid-response
  failures; malformed successful mutations retain unresolved outcome semantics
  when commit outcome cannot be proven.
- Backend Pydantic response models remain canonical wire authority. Proven
  compatibility forms are preserved explicitly rather than inferred from
  optional TypeScript properties.
- GH-139 is the direct validation precedent, not a contract to widen
  indiscriminately.
- Runtime validators should remain capability-local.
- Current backend response models are presumed canonical until discovery proves
  a contradiction.
- Compile-time typing alone is insufficient at a supported remote boundary.
- Exact implementation surface is deliberately deferred until discovery
  classifies every remaining response family.
