# GH-156 — Harden repository script paths and inventory

## Goal

Remove proven repository-script path drift after the Version 2.0 release and make
the maintained script surface accurately discoverable without deleting retained
operator or compatibility tooling that still owns a current contract.

## Outcome

Repository scripts resolve the canonical repository/backend locations in normal
checkouts and linked worktrees, review packages contain canonical Version 2.0
metadata, the script index reflects the maintained entry-point surface, and
mechanical regression coverage protects those contracts.

The post-release inventory is reconciled explicitly. A script is deleted only
if current repository authority proves that it is both unneeded and superseded.

## Non-goals

- Application feature, domain, API, persistence, migration, or schema changes.
- Dependency or toolchain upgrades.
- Reworking the Version 2.0 release.
- Collapsing security-sensitive Phase 5C/5C4 command surfaces merely because
  they contain similar CLI plumbing.
- Deleting historical evidence or retained qualification capability.
- Refactoring shell infrastructure beyond the proven path/discoverability
  defects.

## Background

The exact post-Version-2.0 audit on main identified 15 shell/command entries and
33 Python tooling entries, for 48 total. All shell entries pass `bash -n` and all
Python tooling parses successfully.

The audit proved four concrete path/package defects:

1. `scripts/lib/common.sh` requires `.git` to be a directory, which incorrectly
   rejects linked Git worktrees where `.git` is a file.
2. `scripts/qualify-phase5c4-infrastructure.sh` changes into `apps/backend` but
   resolves Python through the nonexistent/noncanonical root `.venv`.
3. `scripts/start-backend.sh` retains a root `.venv` fallback even though the
   repository-owned backend environment lives at `apps/backend/.venv`.
4. `scripts/zip-project.sh` does not include root `VERSION`, now the canonical
   release-version authority.

The script index also omits the ordinary backend baseline and the retained E4-16
and Issue-17 specialist qualification wrappers.

Three scripts had zero current textual references in the mechanical scan:
`export_personal_transfer.py`, `manage_phase5c4_authorization.py`, and
`qualify_immutable_provenance.py`. Current architecture and operations semantics
show that each still owns retained transfer, authorization, or exact-schema
qualification behavior. Lack of a current textual reference is therefore a
discoverability defect, not deletion authority.

4. `scripts/README.md` as the repository script discovery index.

6. Historical production-hardening records only for retained point-in-time

## Allowed changes

- Replace the `.git` directory assumption with Git-aware repository/worktree
  validation.
- Normalize affected Python interpreter selection around
  `apps/backend/.venv/bin/python` plus an explicit supported override where
  appropriate.
- Add canonical root `VERSION` to the review package.
- Add narrow regression tests for these exact contracts.
- Update script discovery/current runbook prose where needed.
- Delete a script only if implementation review proves it has no current
  runtime, operator, transfer, recovery, compatibility, or qualification
  authority and is semantically superseded.

## Forbidden changes

- Application behavior or public API changes.
- Mobile code or configuration changes.
- PostgreSQL or SQLite schema/migration changes.
- Control-plane authorization semantics.
- Weakening qualification or safety checks.
- Converting destructive/specialist qualification into ordinary baseline work.
- Broad Phase 5C/5C4 CLI refactoring.
- Deleting a script solely because its originating Epic/phase is complete.
- Changing Node, Python, dependency, or Version 2.0 metadata authority.

## Escalation conditions

- A candidate script is found to own behavior not represented in current docs.
- Removing or combining a script would alter authorization, signing, migration,
  recovery, transfer, or destructive-operation boundaries.
- A supposedly path-only repair changes application runtime semantics.
- Review packaging cannot include `VERSION` without broadening secret/generated
  content.
- A linked-worktree repair requires weakening repository identity checks.
- Any additional deletion candidate has non-historical references or tests whose
  authority is ambiguous.

## Decisions and assumptions

- The inventory's three zero-current-reference candidates are retained pending
  implementation proof because each still corresponds to a current retained
  capability or operating boundary.
- No current top-level shell entry points should be combined. Their existing
  orchestration/wrapper layering is intentional.
- Similar signerless Phase 5C4 authorization CLIs remain separate because they
  encode distinct purpose-specific authorities.
- `scripts/project-audit.py` is the implementation behind the stable
  `project-audit.sh` entry point and does not require a second public index row.
- Root `.venv` is not a repository-owned Python authority.
- The cleanup should reduce ambiguity, not generalize the scripting framework.

- **GRILLED planning disposition:** Audit findings are concrete and bounded. The three mechanically orphaned tools retain current operational authority, so no deletion is justified from reference count alone. Security-sensitive Phase 5C4 CLIs remain separate.
