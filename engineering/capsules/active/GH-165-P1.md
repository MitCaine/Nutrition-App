# GH-165-P1 — Bootstrap Task Capsule orchestration and remote qualification

## Goal

Reduce deterministic Task Capsule lifecycle friction and establish a repository-owned exact-SHA remote qualification mechanism before any protection is enabled on `main`.

## Outcome

The repository has one authoritative capsule orchestration entry point, a schema-v1 qualification-profile contract, and a GitHub Actions `Main qualification` workflow that can qualify an exact GitHub-visible commit and emit bound machine-readable evidence. P1 proves that mechanism while `main` remains unprotected. P2 owns live ruleset enforcement.

## Non-goals

- Do not enable, modify, or test a live GitHub ruleset or classic branch protection.
- Do not require pull requests, GitHub approving reviews, merge queue, signed commits, or linear history.
- Do not change application product behavior, persistence behavior, migrations, APIs, or mobile feature code.
- Do not implement the future `ios-native` profile; AUDIT-09 / issue #167 owns that work.
- Do not implement residual dependency-risk handling; AUDIT-08 / issue #166 owns that work.
- Do not close issue #165 during P1.

## Background

Issue #165 was created from AUDIT-07 after repository-scale review found that the existing Task Capsule workflow provides useful scope, verification, and review discipline but leaves repetitive lifecycle mechanics manual and leaves `main` mechanically unprotected.

Read-only discovery at external evidence checkpoint `GH-165-discovery-20260824-001130` established:

- `main`, local `main`, and `origin/main` at base commit `233938a941654e6eb8b0d46d30b3bfa4beb28879`;
- zero active task capsules and 78 terminal HISTORY records;
- general capsule and documentation validation passing;
- GitHub issue #165 open;
- repository public with admin/push authority available;
- zero repository rulesets and no classic `main` protection;
- ruleset and applicable-rules APIs available;
- current successful check surface consists of Backend baseline, Backend PostgreSQL 16 contracts, Mobile baseline, Repository validation, and three CodeQL Analyze checks;
- no existing first-class capsule orchestration entry point.

- [x] AC-1: One repository-owned capsule orchestration entry point can report capsule status and perform the deterministic mechanics for legal lifecycle transitions while refusing illegal transitions and preserving append-only State History.
- [x] AC-2: The orchestrator fails closed for stale base authority, wrong branch/worktree identity, dirty or drifted worktrees, unexpected owned/allowed/forbidden scope including untracked files, blocked capsules, and other existing execution-preflight violations; it must also operate from linked task worktrees without requiring a duplicate ignored `apps/backend/.venv`, using the repository's supported canonical Python authority.
- [x] AC-3: Schema-v1 `specialized_qualification` supports deterministic `profile:PROFILE_NAME` declarations without adding an unknown metadata key or weakening existing readiness invalidation; profile changes after READY remain execution-contract changes.
- [x] AC-4: The implemented qualification registry supports the current `repository`, `backend`, `mobile`, and `postgresql` profiles through repository-owned commands/workflow logic; unknown or unavailable profiles fail closed.
- [x] AC-5: A stable GitHub Actions check/workflow named `Main qualification` can receive/bind task ID, capsule revision, exact commit SHA, and selected profiles, checks out and verifies the exact requested SHA, runs the declared profiles, and fails on identity/profile mismatch.
- [x] AC-6: An exact committed P1 checkpoint is published to a temporary GitHub-visible qualification ref, receives successful `Main qualification` evidence for its declared profiles, and the temporary ref can be removed without updating `main` or enabling branch enforcement.
- [x] AC-7: Successful remote qualification emits deterministic machine-readable evidence binding task ID, capsule revision, exact SHA, selected profiles, per-profile outcomes, workflow/check identity, and overall result; failure evidence remains inspectable and cannot be reported as PASS.
- [x] AC-8: Automation leaves acceptance-criterion judgment, review disposition, architecture/scope-stop decisions, failed-check waivers, and human-owner MERGED authority outside automated decision making.
- [x] AC-9: Current process/script/testing documentation identifies the canonical capsule command, qualification-profile syntax, remote qualification flow, evidence contract, and P1/P2 bootstrap boundary without duplicating conflicting authority.
- [x] AC-10: P1 makes no live GitHub ruleset/classic-protection mutation, does not close issue #165, and leaves application runtime, migrations, mobile product code, and existing architectural authority unchanged.

## Escalation conditions

- Stop if schema-v1 cannot represent profile declarations without weakening capsule validation.
- Stop if exact-SHA qualification cannot be bound unambiguously to the requested commit.
- Stop if GitHub requires a PR-centric workflow or a routine bypass to produce the required remote check.
- Stop if implementing the qualification workflow requires enabling `main` protection before P1 is reviewed.
- Stop if existing CI semantics would be weakened, skipped, or materially changed merely to simplify `Main qualification`.
- Stop if required work crosses application runtime, migration, or mobile product boundaries.
- Stop if an unexpected GitHub repository setting/resource mutation occurs.
- Stop if a material P1 contract change is required after READY; return to DECOMPOSED, increment capsule revision, and requalify.

## Decisions and assumptions

- The parent AUDIT-07 work is decomposed into P1 bootstrap automation/qualification and P2 live governance enforcement.
- P1 deliberately leaves `main` unprotected; P2 enables enforcement only after P1 is proven.
- Existing schema-v1 `specialized_qualification` is the qualification-profile authority using `profile:PROFILE_NAME` tokens; no schema-version change is planned.
- P1 profiles are `repository`, `backend`, `mobile`, and `postgresql`.
- `github-resource` enforcement is deferred to P2 because it depends on live GitHub governance state.
- `ios-native` is deferred to issue #167.
- The existing Task Capsule reasoning gates remain authoritative; automation owns mechanics, not engineering judgment.
- PRs, GitHub approvals, merge queue, signed commits, linear history, and routine bypass remain non-requirements.
- No Codex or other delegated coding agent is authorized; delegation remains `none`.
- Pre-READY execution exposed that linked Git worktrees do not inherit ignored `apps/backend/.venv` state; P1 must make canonical tooling usable from such worktrees without requiring per-worktree virtual-environment duplication.
