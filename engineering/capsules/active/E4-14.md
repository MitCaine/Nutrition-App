# E4-14 — Add grouped More nutrients authoring for extended catalog fields

## Goal

Keep the complete canonical nutrient catalog authorable without returning manual Food create/edit to a giant flat nutrient form.

## Outcome

New Food and Edit Food use one grouped `More nutrients` discovery interaction for extended canonical nutrients. The conventional Nutrition Facts set remains the ordinary authoring baseline. Existing populated extended nutrients remain visible on edit. Newly selected extended nutrients begin as unknown and use the existing nutrient-value/status authority when the user enters or omits an amount.

## Non-goals

- No canonical nutrient catalog, ID, kind, unit, hierarchy, or display-order changes.
- No backend, API, runtime, SQLite, migration, OCR, USDA, or Recipe changes.
- No new nutrient persistence representation.
- No automatic zero inference.
- No giant `Show All` mode.
- No separate create and edit discovery implementations.
- No regulatory-label authoring or certification behavior.
- No new estimated-value status control beyond existing Food nutrient entry semantics.
- No E4-15 durability work.

## Background

E4-13 restricted New Food to the accepted conventional fifteen Nutrition Facts fields while retaining the complete canonical nutrient collection in the existing Food form/payload model. Hidden extended nutrients therefore remain authoritative `unknown` values rather than disappearing from the mutation contract or becoming invented zeros.

Edit currently preserves populated extended nutrients, but its missing-nutrient discovery is an edit-only `Add missing nutrient` disclosure inside `NutrientEntryList`.

E4-14 owns replacing that transitional asymmetry with the accepted grouped `More nutrients` interaction shared by create and edit.

The Feature PRD explicitly requires Vitamins, Minerals, and Fatty Acids. The existing canonical section model also contains an `Other` bucket, and canonical nutrients classified there must not become inaccessible because the accepted product invariant keeps the full canonical catalog available. `Other` therefore remains a trailing compatibility bucket when such candidates exist. This does not alter canonical nutrient classification.

## Authority and precedence

1. GitHub #127 and the Epic 4 Feature PRD own E4-14 product behavior.
2. Existing `useFoodForm` remains the sole Food authoring value/payload authority.
3. Existing canonical nutrient definitions remain the sole nutrient identity/unit/kind/order authority.
4. Existing `groupCanonicalNutrientsBySection` remains the grouping authority.
5. Existing `NutrientEntryList` amount/status transitions remain authoritative for unknown, zero, known, and preserved estimated values.
6. E4-13 remains authoritative for the conventional Nutrition Facts baseline and populated extended-value preservation.

## Owned surface

### Ordinary visible fields

New Food immediately exposes the conventional fifteen Nutrition Facts nutrients established by E4-13.

Edit Food retains that same conventional authoring baseline and additionally surfaces every already-populated extended nutrient without requiring discovery again.

An extended nutrient selected during the current form session joins the ordinary visible nutrient fields.

### More nutrients

A single `More nutrients` action is available in both New Food and Edit Food whenever undisplayed extended canonical nutrients remain.

It is collapsed by default.

Opening it exposes grouped candidates in this order:

1. Vitamins
2. Minerals
3. Fatty Acids
4. Other, only when remaining canonical candidates require the existing compatibility bucket

The first three groups are the accepted product groups. `Other` is not a new catalog category; it preserves reachability of already-canonical nutrients whose existing kind maps there.

Conventional Nutrition Facts nutrients are not candidates because they are already part of the ordinary authoring baseline.

Already-populated or already-selected extended nutrients are not candidates.

Selecting a nutrient:

- uses the existing canonical nutrient definition;
- reveals the existing form-model value;
- leaves that value `unknown` until the user enters an amount;
- closes the disclosure so the newly added field becomes the immediate editing target/surface;
- does not create a second nutrient record or state owner.

`Cancel` closes the disclosure with no nutrient-value or selected-field change.

Reopening recalculates the remaining candidate set from the same canonical definitions and current visible selection.

### Omit and re-add

For a conventional Nutrition Facts nutrient, `Omit` continues to mean unknown while the conventional field remains part of the baseline.

For an extended nutrient selected during this session, returning it to unknown removes it from the ordinary visible extended-field set and makes it available through `More nutrients` again.

For an existing saved extended nutrient, untouched persisted known/estimated/zero data must remain visible and preserve its exact semantics. If the user explicitly omits it, it becomes unknown under the existing mutation contract and may return to discovery.

There is no separate persisted concept of “selected but unknown.” Unknown remains the authoritative nutrient-data state.

- Add Food-authoring helpers that distinguish conventional versus extended canonical nutrient definitions without changing catalog data.
- Refactor `NutrientEntryList` presentation state so create and edit share one `More nutrients` discovery model.
- Maintain a presentation-only set of currently revealed/selected extended nutrient IDs.
- Keep conventional fields visible independently of unknown status.
- Seed visible extended IDs from populated Food nutrient values on edit.
- Group undisplayed extended candidates through the existing canonical section helper.
- Add `More nutrients` and `Cancel` disclosure controls with accessible expanded state.
- Remove the transitional edit-only `Add missing nutrient` wording/flow.
- Update directly affected E4-13 and Food-form regressions where their expectations are intentionally superseded by E4-14.
- Add dedicated E4-14 rendered-screen/state qualification.
