# GH-155-R1 — Establish coherent Version 2.0 release authority

## Goal

Complete GitHub issue #155 with one truthful Version 2.0 source-release
authority while preserving the repository lifecycle ordering between
pre-integration verification and post-REVIEWED publication.

## Outcome

Version 2.0 has one canonical repository version authority, coherent current
mobile/backend/documentation mirrors, truthful current remote-runtime startup
guidance, qualified Node 24 and Python 3.12 support, and a concise release
record.

The implementation is fully qualified and independently reviewed before human
integration. After the exact reviewed tree is integrated to the default branch,
a separate mandatory publication gate requalifies that exact integration
commit, rechecks security state and GitHub checks, publishes one annotated
`v2.0.0` tag and one GitHub Release, and only then permits the capsule to
advance from REVIEWED to MERGED/archive.

## Non-goals

- Do not rewrite migration history.
- Do not weaken the 0021 activation boundary.
- Do not introduce an unqualified `alembic upgrade head` workflow.
- Do not redesign runtime authority.
- Do not reopen GH-153 or GH-154.
- Do not rewrite historical Version 1.0/1.1/1.2 planning or release evidence.
- Do not add native App Store/Play Store build identifiers.
- Do not upgrade dependencies merely to suppress the three known
  Expo/toolchain alerts.
- Do not create a tag or GitHub Release during implementation, VERIFIED, or
  independent REVIEWED qualification.
- Do not treat the predecessor GH-155 frozen planning package as executable
  authority without successor lifecycle qualification.

Two distinct qualification phases are mandatory.

Pre-integration source qualification:

1. qualify exact implementation content;

4. conduct independent review and reach REVIEWED with no tag/release published.

Post-REVIEWED publication qualification:

1. human-integrate the exact reviewed tree to the default branch while the task
   capsule remains REVIEWED;
2. bind the exact integration commit and prove its tree equals the reviewed
   tree;
3. rerun/finalize the complete release qualification against that exact
   integration commit;
4. recheck Dependabot, code scanning, and secret scanning;
5. require all repository-required GitHub checks on that integration commit to
   succeed;
6. freeze the final publication qualification;
7. create exactly one annotated `v2.0.0` tag targeting that exact integration
   commit;
8. push the tag once and verify the tag object and peeled commit;
9. create exactly one GitHub Version 2.0 Release from that existing verified
   tag;
10. verify the published Release record against repository release notes and
    exact integration identity;
11. only after steps 1-10 may REVIEWED advance to MERGED in the separate archive
    checkpoint;
12. close issue #155 only after the MERGED archive passes post-push
    qualification.

Any failed final qualification, changed security disposition, conflicting
existing tag/Release, or need for source correction stops publication.
