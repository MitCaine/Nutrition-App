# GH-155 — Establish coherent Version 2.0 release authority

## Goal

Make repository startup guidance, executable version metadata, current product
documentation, qualification evidence, tag identity, and GitHub release
artifacts tell one truthful Version 2.0 story.

## Outcome

Version 2.0 has one explicit release-version authority, one truthful supported
remote-development startup story, deliberately qualified Node 24 / Python 3.12
toolchain support, final release documentation and upgrade guidance, and an
annotated `v2.0.0` tag plus GitHub Release bound to the exact final qualified
release commit.

## Non-goals

- Do not rewrite historical migration history.
- Do not weaken or bypass the special migration/activation safety boundary.
- Do not introduce an unqualified `alembic upgrade head` workflow.
- Do not redesign runtime authority or application architecture.
- Do not reopen or broaden GH-153 or GH-154.
- Do not rewrite historical planning or release evidence merely to make old
  material use current terminology.
- Do not change native build identifiers until their Version 2.0 release role
  is explicitly inventoried and decided.
- Do not create `v2.0.0` or a GitHub Release before the exact final release
  commit has completed the required final qualification.

## Background


GitHub issue #155 is the final pre-2.0 release-coherence track.

The pre-2.0 audit found three related forms of release drift:

1. Documentation examples stop at migration
   `0020_immutable_provenance_enforcement`, while current runtime/schema
   authority is `0033_complete_runtime_authority`.
2. Current product documentation identifies Version 1.2 while executable
   package/API metadata still reports `0.1.0`.
3. No final Version 2.0 tag or GitHub Release exists.

## Escalation conditions

- Current remote-development initialization cannot reach current schema/runtime
  authority without violating the special activation contract.
- Existing documentation and executable behavior disagree about supported remote
  startup semantics.
- More than one plausible canonical version authority exists and precedence
  cannot be resolved from repository contracts.
- Version propagation requires unrelated runtime, API, database, migration, CI,
  package-management, or architecture changes.
- Native build identifiers imply a distributable-build workflow not covered by
  the qualified release contract.
- The final release commit fails any required qualification.
- Dependency/security recheck reveals a release-blocking issue.
- Existing Git tag or GitHub Release identity conflicts with `v2.0.0`.
- Any post-READY authority, scope, acceptance, risk, qualification, delegation,
  or escalation change becomes necessary.
- Publication would require claiming support or qualification not actually
  demonstrated.
