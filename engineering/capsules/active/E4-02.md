# E4-02 — Make Complete assertion deterministic and mutation-recoverable

## Goal

Expose one reliable mark-Complete mutation through the existing Daily Logs capability so local and remote authorities confirm the same positive date-owned state, remote indeterminate outcomes can be reconciled without guessing, and a date cannot be marked Complete while the client still has unresolved nutrition-changing work for that date.

## Outcome

`DailyLogsRuntime` exposes a bounded Complete mutation with authoritative completion evidence and deterministic mutation identity. Local SQLite applies the Complete assertion and its mutation receipt atomically. Remote FastAPI/PostgreSQL reuses the existing owner/operation/request receipt machinery and mutation-status endpoint semantics. Same-intent replay returns the prior committed result, changed-payload reuse conflicts, future and empty dates fail explicitly, and the existing client recovery journal can reconcile an indeterminate Complete submission while also exposing a deterministic same-date nutrition-mutation gate for the later UI.

## Non-goals

- No Complete button, Daily Log layout change, History UI, or other user-facing screen work; E4-07 and later tasks own presentation.
- No automatic Complete invalidation after create/edit/delete/move; E4-03 owns that transaction coupling.
- No manual clear/un-complete mutation.
- No History range reads, projections, averages, or chart/cache implementation.
- No synchronization, offline mutation queue, background replication, fallback, or mixed-authority recovery.
- No backup/restore or one-time-transfer propagation of Complete; E4-15 owns those semantics.
- No new application-data capability or ninth `NutritionRuntime` capability.

## Background

E4-01 merged date-owned positive Complete persistence to `main` at `a2f03bc8782cdd3dd51e9f6dcc5be9808c01ee87`; the repository baseline for this task is the later bookkeeping-clean `main` commit `d320f1f73a73dcb435c6f101ef4ae429cebcb3e5`. Remote Daily Log update/delete mutations already reserve owner/operation/request receipts in `create_operation_idempotency`, complete the receipt and domain mutation in one transaction, and expose terminal/recoverable status through `/logs/mutations/{client_request_id}`. The local Daily Logs runtime already mirrors deterministic mutation receipts, while `logMutationRecovery.ts` durably journals exact submitted payloads and source/destination dates for reconciliation. E4-02 extends these existing mechanisms with Complete semantics instead of adding parallel recovery or persistence systems.

## Decisions and assumptions

- Canonical Complete receipt operation is semantically `complete` under the existing Daily Log mutation namespace; transport/storage naming may follow established `log.*` conventions but must normalize to one public status operation.
- The Complete response carries semantic equivalents of `logged_date` and authoritative `completed_at`; it does not create a second resource ID for the date-owned assertion.
- The existing generic receipt's UUID `resource_id` is receipt-internal for Complete and must not become a second application identity. If a safe use cannot be demonstrated without schema change, escalate.
- Same client-request identity plus same canonical Complete payload is replay; same identity plus any changed canonical request field is conflict, matching existing mutation policy.
- Different client-request identities may validly assert an already-Complete eligible date and converge on the same date-owned state; they must not create duplicate Complete rows.
- Client recovery gating is authority-scoped workflow state, not a second application-data authority. It prevents a new Complete submission while same-date nutrition mutation outcome is unresolved but does not decide whether the authoritative date is Complete.
- A recovery-journal schema extension must be explicitly versioned if older code would not recognize the new record shape; existing version-2 unresolved records remain recoverable after upgrade.
- E4-02 does not invalidate Complete after later nutrition changes; E4-03 is required before that invariant is complete end-to-end.
- Capsule revision 2 records the strict execution-preflight PASS and transition to bounded implementation; product scope and ownership are unchanged.
- Capsule revision 3 allows local-foundation decoration as the narrow wiring seam for Complete while leaving the established local create/update/delete implementation structurally untouched.
- Capsule revision 4 records completed implementation qualification and independent PASS review of `c886cb5aee4153413bd879cc33267dbb2c53e14a`; no application behavior changed in this bookkeeping revision.
