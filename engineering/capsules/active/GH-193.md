# GH-193 — Guarded integration and recoverable terminal closeout

## Goal

Make candidate integration, separate terminal qualification, HISTORY recovery, and reconciliation one controller-owned transaction with explicit checkpoints.

## Outcome

An operator can resume one bounded controller transaction from any interruption. It accepts only the exact reviewed implementation and separately qualified terminal commit, verifies protected main and recovery, then closes the issue and cleans only identified disposable work.

## Non-goals

No new GitHub App, ruleset mutation, candidate source rewrite, private Poker code copy, product change, automatic reviewer approval, or promotion of the combined workflow. #194 pilots promotion.

## Background

GH-188–GH-192 are integrated. `scripts/task.py` already validates live external authorization, exact candidate/App check, independent review, owner flag, and reconciles an interrupted protected push. Terminal HISTORY and capsule removal currently require a second manually orchestrated candidate/authorization/check. Existing helper rejects capsule lifecycle updates after the implementation main advances. Preserve its fail-closed behavior while adding a narrow terminal path.

## Authority and precedence

Owner authorized sequential issue implementation. GitHub #193, this frozen capsule, external authorization, Nutrition workflow contracts, and protected-main ruleset govern. Planning publication is a separate narrow, qualified protected-main update; no direct bypass.

## Dependencies and prerequisites

Main is exact GH-192 terminal SHA above and issue #193 is open. P must be a capsule-only direct child. The candidate and terminal stages each require their own exact external authorization, dedicated-App qualification, verification and independent review. No check or verdict transfers between SHAs.

## Owned surface

Trusted task controller/closeout helper, focused controller and closeout tests, capsule, and operator workflow documentation. HISTORY is an output of the operation on a later separately authorized terminal candidate, not an implementation-owned file.

## Allowed changes

Add a resumable closeout operation with durable intent and exact recovery validation. Keep the existing separate `integrate` entrypoint as the guarded implementation stage during migration. Expose deterministic preparation/check/reconcile stages rather than silently granting review or terminal qualification.

## Forbidden changes

No force push, bypass, changed App identity, unqualified main update, automatic owner approval, fabricated reviewer verdict, deletion of dirty/unrelated work, duplicate HISTORY record or per-task completed archive.

## Acceptance criteria

- [ ] AC-1: At integration/recovery time, revalidate current external authorization, capsule revision, exact candidate, old main, required profiles, App check, attached independent review/RI disposition and owner approval.
- [ ] AC-2: Protect exact reviewed source; moved main, changed authority, stale check/review or wrong branch tip stops without force.
- [ ] AC-3: Planning publication is explicitly treated as a separate narrow, exact qualified protected-main update with no bypass.
- [ ] AC-4: Full REVIEWED capsule has reachable commit/path and SHA-256; one MERGED/CANCELLED HISTORY record and active-file removal form the terminal diff, with no archive.
- [ ] AC-5: Terminal SHA has separate bound external authority, repository qualification, verification and independent review; no implementation check reuse.
- [ ] AC-6: Durable intent and remote reconciliation verify main, ancestry/source continuity, terminal scope, HISTORY recovery and active removal; repeat invocation is safe after partial success.
- [ ] AC-7: Owning issue updates and narrowly authorized disposable cleanup occur only after verified terminal success; dirty, unrelated, failed and recovery work survive.
- [ ] AC-8: Negative tests cover separate C/T SHA, moved main, stale/wrong App check, missing owner approval, duplicate HISTORY, interrupted push, failed terminal qualification and dirty/wrong cleanup refusal.
- [ ] AC-9: A disposable end-to-end proof traverses the actual protected path without changing branch protection; repository baseline and fresh independent review pass.

## Required verification

### Focused

Task controller and closeout tests, including deterministic negative and interrupted transaction cases.

### Baseline

Repository profile, capsule/history validation, review bundle, and whitespace checks.

### Specialized qualification

Exact candidate repository profile through dedicated App4708441. No product/native/database profile is required for tooling-only implementation. Separate terminal candidate proof is mandatory.

## Return evidence

Exact B/P/C/T and authorization IDs, full recovery SHA/path/hash, negative tests, protected checks, independent review, remote reconciliation, issue status and retained-work inventory.

## Escalation conditions

Authority/check/profile/review mismatch, non-exact main, unverifiable recovery, dirty cleanup target, unavailable protected qualification or any unexpected remote mutation stops the transaction. Preserve diagnostic and failed candidate evidence.

## Decisions and assumptions

The transaction can checkpoint between candidate integration and terminal qualification/review; it may not claim terminal completion until a distinct qualified/reviewed terminal SHA is accepted. The controller never synthesizes an independent review or an owner approval. Planning publication follows the existing exact protected path.
