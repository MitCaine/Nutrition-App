# GH-165-P3 — Replace candidate-controlled qualification with trusted task controller

## Goal

Build the candidate-independent task authorization, trusted qualification, dedicated-App check
publisher contract, and automated `./scripts/task` operator interface needed to replace Task
Capsules as the security authority. P3 is the bootstrap implementation that must first become
reviewed code on `main`; the first live task using that implementation is deliberately deferred to
GH-165-P4.

## Outcome

The repository contains a reviewed, deterministic replacement controller that is ready to become
the default-branch trust root. `./scripts/task` owns routine mechanics; GitHub Issue authorization
is outside candidate history; the trusted workflow is explicitly dispatched from `main`; candidate
qualification executes without the dedicated-App credential; and a separate finalizer is capable of
publishing an exact-SHA `Main qualification` check through a dedicated App.

All contracts are proven with deterministic fakes and repository tests in P3. No live App secret,
ruleset, or protected-main mutation occurs in P3. After P3 is integrated, GH-165-P4 provisions the
live App, uses this controller for its own disposable pilot, proves GitHub behavior, activates
protection only after successful proof, and supplies the owner-facing workflow evaluation.

## Non-goals

- Do not weaken independent verification, independent review, or explicit human merge authority.
- Do not make pull requests, GitHub approving reviews, merge queue, or linear history mandatory
  merely to replace Task Capsules.
- Do not require candidate repository history to prove its own authorization.
- Do not expose the dedicated GitHub App private key to candidate-executing jobs.
- Do not change product runtime behavior, migrations, dependency versions, or mobile native code.
- Do not delete the existing capsule machinery until the replacement pilot is proven and reviewed.
- Do not activate main protection before the trusted check source is proven on a disposable task.

## Background

GH-165-P2 successfully automated substantial capsule and exact-SHA qualification mechanics, but
independent review proved a systemic trust defect: a candidate lineage could author its own READY
authority, and a qualification ref could replace the GitHub Actions workflow that produced a
same-named `Main qualification` check. Binding the required status to the generic GitHub Actions App
therefore did not identify the reviewed qualification producer.

The replacement keeps the proven reasoning gates but moves security authority outside candidate
history.

## Allowed changes

  remove candidate-history authority assumptions.
- Add a trusted `workflow_dispatch` qualification workflow intended to execute from `main`.
- Add machine-readable task authorization and state/evidence formats backed by GitHub Issue
  comments.
- Keep the legacy capsule CLI available during migration and document it as transitional after the
  pilot proves the replacement.
- Add bounded regression fixtures that simulate forged authorization, candidate-controlled
  workflows, stale base, scope violations, failed suites, and check-source spoofing.

## Forbidden changes

- No product runtime, database migration, dependency/toolchain, OCR, native-module, or package-lock
  changes.
- No ruleset activation during bootstrap implementation.
- No routine bypass of failed qualification.
- No App credential in repository files, artifacts, candidate worktrees, candidate jobs, or logs.
- No automatic acceptance decision, automatic review approval, or automatic human-merge decision.
- No deletion of legacy capsule authority before the disposable replacement pilot is accepted.

## Acceptance criteria

- [x] AC-1: `./scripts/task` is the single stable replacement entry point, exposes deterministic task-controller commands, and emits compact JSON/checkpoint summaries suitable for human or automated callers.
- [x] AC-2: The authorization format is external to candidate Git history and canonically binds issue/task identity, exact base SHA, allowed paths, forbidden paths, qualification profiles, revision, nonce, authorization comment ID, trusted author identity, and SHA-256 digest.
- [x] AC-3: Authorization validation fails closed on wrong author, wrong issue, malformed/duplicate authority, edited content/digest mismatch, stale base, unsupported profile, or ambiguous authorization; deterministic GitHub API fakes cover positive and negative cases.
- [x] AC-4: Candidate scope is calculated from the externally authorized base to the exact candidate SHA; forbidden or unexpected paths fail closed and candidate files cannot broaden scope or reduce qualification profiles.
- [x] AC-5: `.github/workflows/trusted-qualification.yml` is structurally a default-branch `workflow_dispatch` controller whose inputs identify an external authorization and exact candidate SHA/ref rather than selecting candidate workflow code as the authority.
- [x] AC-6: Trusted qualification reuses the existing repository profile suites through trusted default-branch workflow code; candidate code is checked out only at the exact supplied SHA and candidate-executing jobs receive no dedicated-App credential.
- [x] AC-7: A separate privileged finalizer executes no candidate code, obtains a dedicated GitHub App token only in that trusted job, revalidates authorization/result binding, and constructs `Main qualification` on the exact candidate SHA.
- [x] AC-8: Dedicated-App check publication is injectable and deterministically tested for exact SHA, check name, conclusion, source/config identity, duplicate/mismatched evidence, failed-suite behavior, and API failure without requiring a live private key.
- [x] AC-9: Main-governance planning accepts a reviewed dedicated-App integration ID rather than the generic GitHub Actions integration and produces loose required-status semantics, no routine bypass, and force-push/deletion protection without applying a live ruleset in P3.
- [x] AC-10: `task qualify` mechanics validate external authority locally, publish only the exact candidate ref required for remote checkout, dispatch the trusted workflow explicitly at `main`, bind issue/comment/digest/SHA inputs, wait for the exact workflow/App-check identity, fail closed on drift, and clean the temporary ref; transport is fully fakeable for P3 tests.
- [x] AC-11: Verification, review, and integration controller contracts preserve explicit reasoning boundaries: automation may gather evidence and enforce prerequisites but cannot infer acceptance, mark review Approved, or authorize the human merge without explicit caller input.
- [x] AC-12: Documentation defines the bootstrap/cutover boundary, dedicated-App minimum permission/secret isolation, compact future operator flow, legacy-capsule compatibility period, and GH-165-P4 live-pilot procedure; all affected repository tests and baseline review pass before P3 approval.

## Escalation conditions

- GitHub cannot bind the required check to the dedicated App integration.
- The App check cannot be created on an arbitrary exact repository SHA.
- Candidate code can access the App credential or execute in the privileged finalizer.
- `workflow_dispatch` cannot maintain a default-branch workflow trust boundary while testing the
  exact candidate.
- External authorization cannot be made unambiguous and fail-closed.
- Main protection semantics differ materially from the reviewed model.
- Replacement requires mandatory PRs/merge queue or another workflow-policy change not explicitly
  reviewed.
- Product/runtime changes become necessary.
- Any proposed shortcut makes candidate code authoritative over its own authorization or final
  required check.

## Decisions and assumptions

- Retain the proven human/reasoning gates while automating deterministic mechanics.
- Use GitHub Issues/comments as candidate-independent task authorization.
- Use a canonical authorization payload plus exact comment ID and SHA-256 rather than repository
  READY history as future execution authority.
- Run authority-sensitive `./scripts/task` commands from trusted `main`, while passing task
  worktrees/candidate SHAs as data.
- Dispatch trusted qualification explicitly against the default branch (`main`); candidate refs
  supply checkout data only.
- Reuse the established repository qualification profiles instead of creating a second test matrix.
- Candidate-executing jobs never receive the dedicated-App private key or installation token.
- A distinct trusted finalizer owns dedicated-App token creation and authoritative check
  publication and does not execute candidate code.
- P3 implements and proves these contracts without live credentials or governance mutation.
- After P3 integration, GH-165-P4 becomes the first live task-controller pilot: provision the App,
  prove exact-SHA check publication/source identity, demonstrate forged/out-of-scope/fake-check
  rejection, activate the ruleset only after those proofs pass, and let the owner evaluate the
  operator flow.
- Task Capsules remain the bootstrap harness through P3 only. Retirement is decided after the P4
  pilot rather than assumed by P3 implementation.

- Revision 2 execution and review-repair evidence remains recoverable at exact IMPLEMENTED checkpoint `8602eb53e7dc11049925915149f7af4305d599f3` and local safety ref `refs/backup/GH-165-P3/revision-2-pre-GH-168`.
