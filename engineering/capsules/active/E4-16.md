# E4-16 — Qualify History parity, failure behavior, and physical chart usability

## Goal

Produce explicit release evidence that the completed Epic 4 History and Complete semantics remain equivalent across local SQLite and remote PostgreSQL authorities, remain correct under difficult failure and calendar states, survive supported durability boundaries, and remain usable on the target iPhone.

## Outcome

A reproducible automated qualification harness deliberately exercises the accepted difficult-state matrix rather than relying on incidental coverage from ordinary populated-day tests.

Equivalent local SQLite and physical PostgreSQL 16 evidence must feed the same shared History projection semantics. Automated evidence is paired with a final integrated target-iPhone qualification of the already-accepted History and Daily Log experience.

Any production defect discovered by qualification stops execution and returns to the controller for bounded scope revision before repair.

## Non-goals

- No new History product behavior.
- No 90-day or custom range.
- No trend judgment, adherence, coaching, reward, or prior-period comparison.
- No historical target reconstruction.
- No new runtime capability.
- No fallback, mixed-authority read, dual read, synchronization, replication, or merge behavior.
- No Daily Log, Complete, History, backup, or transfer persistence redesign.
- No migration.
- No general runtime-response validation refactor from #139.
- No CI workflow change from #140.
- No reopening of the already evidence-driven 30-day horizontal-scroll decision.
- No accessibility-specific chart qualification beyond preserving existing behavior.

## Background

E4-16 is the final explicit cross-authority, failure-behavior, durability, and physical-use qualification task for Epic 4.

The individual implementation slices already provide substantial evidence:

- E4-03 owns atomic Complete invalidation, exact-snapshot preservation, serving-equivalent preservation, and source/destination mutation behavior.
- E4-04 owns bounded History range evidence, missing dates, `firstLoggedDate`, Complete evidence, canonical units, local/remote adapter parity, and physical PostgreSQL owner isolation.
- E4-05 owns the shared History calculation layer, Complete/Logged denominators, nutrient-specific usable-day counts, known/estimated/zero/unknown distinctions, exact-decimal arithmetic, and parent non-manufacture.
- E4-06 owns authority/range cache identity, late-response suppression, same-range stale refresh behavior, overlap-specific mutation invalidation, target independence, and remote failure without fallback.
- E4-09 owns Today exclusion, 7/30 periods, earliest partial periods, whole-period paging, month/year transitions, and DST-safe LocalDate arithmetic.
- E4-15 owns Complete durability through coherent local backup/restore and versioned one-time PostgreSQL-to-SQLite transfer.

Physical qualification also exists at the component level:

- E4-10 physically established that static 30-bar presentation was not sufficiently usable and implemented the accepted bounded horizontal-scroll adaptation with all 30 observations retained and 44-point daily slots.
- E4-11 physically qualified the distinct scrollable Nutrition Details surface and grouped nutrient interaction.
- E4-12 physically qualified focused nutrient charts, Daily values, 7/30 behavior, exact date navigation, and History return context.

E4-16 therefore consolidates and strengthens proof. It does not reimplement those contracts.

GitHub #140 is completed and archived. Ordinary PostgreSQL CI now durably selects the completed E4-01 through E4-04 PostgreSQL product-contract suites. E4-16 still runs those suites explicitly as part of its own release-evidence harness, while `.github/workflows/ci.yml` remains outside this capsule.

GitHub #139 tracks broader remote runtime response validation. E4-16 preserves accepted remote failure/no-fallback semantics but does not absorb that refactor unless qualification exposes a concrete malformed-History-response correctness blocker.
