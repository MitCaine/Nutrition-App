# GH-162 — Fail closed on Python 3.12 before creating the backend virtual environment

## Goal

Prevent the documented preserved-backend setup flow from creating `apps/backend/.venv` with an
unsupported host/default Python before the repository-owned Python 3.12 requirement is checked.

## Outcome

Both current backend setup guides use one explicitly selected interpreter for repository toolchain
verification and virtual-environment creation. The environment-creation command is conditional on
`scripts/toolchain-report.py --check python` succeeding, so an unsupported default interpreter
cannot create `.venv`. The existing project-audit document contract prevents regression to the
unguarded `python3 -m venv .venv` sequence.

## Non-goals

- Do not change the repository-supported Python version or backend `requires-python`.
- Do not add, require, or recommend a particular Python version manager.
- Do not change `scripts/toolchain-report.py` or its version-matching semantics.
- Do not change backend application, migration, persistence, API, or runtime behavior.
- Do not regenerate dependency or lock files.
- Do not change mobile setup or Node authority.
- Do not broaden this task into general onboarding or environment-management redesign.

## Background

Post-GH-159 audit item `AUDIT-04` identified that the root README and current development guide each
run `python3 -m venv .venv` before proving that `python3` satisfies repository authority.

Discovery at the frozen base established:

- `.python-version` is `3.12`.
- `apps/backend/pyproject.toml` requires `>=3.12,<3.13`.
- The audited host resolves default `/usr/bin/python3` to Python 3.9.6.
- Running `python3 scripts/toolchain-report.py --check python` with that default returns exit 1 and
  reports `ERROR TOOLCHAIN_MISMATCH`.
- `/opt/homebrew/bin/python3.12` reports Python 3.12.13 and passes the same repository check.
- Both current setup documents contain exactly one unguarded `python3 -m venv .venv`.
- `scripts/toolchain-report.py --check python` already provides the necessary fail-closed authority.
- `scripts/project-audit.json` already provides current-document required/forbidden contracts for
  both affected documents.
- Existing `test_toolchain_report.py` and `test_project_audit.py` pass and already exercise the
  underlying toolchain and generic document-contract machinery.

## Decisions and assumptions

- Use the existing `scripts/toolchain-report.py --check python` authority rather than inventing a
  second Python-version check.
- Use one `PYTHON_BIN` value for both verification and venv creation so the verified interpreter is
  necessarily the interpreter that creates `.venv`.
- Default `PYTHON_BIN` to `python3`; on a host where that is unsupported, the check fails before
  venv creation.
- Permit users to set `PYTHON_BIN` to a compatible Python 3.12 executable such as `python3.12`
  without prescribing how that interpreter was installed.
- Use shell conditional execution for the check/create pair so the documented contract itself,
  rather than prose alone, prevents unsupported venv creation.
- `scripts/project-audit.json` is sufficient as the task-specific regression surface because the
  repository already mechanically applies and tests generic operator-document contracts.
- Existing toolchain and project-audit test source remains evidence-only unless implementation
  disproves that assumption, in which case READY is invalidated and the task returns to DECOMPOSED.
- Terminal closeout will use the simplified order adopted after GH-163: integration qualification,
  explicit issue closure, one terminal HISTORY closeout commit, remote closeout qualification, then
  branch/worktree cleanup.
