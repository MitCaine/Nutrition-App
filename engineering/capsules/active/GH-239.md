# GH-239 — Reject forbidden changes in intermediate candidate commits

## Goal

Prevent a forbidden intermediate commit from entering protected main when its final candidate tree hides that change.

## Outcome

Every commit introduced after the authorized base obeys the same allowed/forbidden path policy, and the final overlay and profile checks remain intact.

## Non-goals

- No change to path-glob semantics; issue #244 owns that separate contract.
- No application behavior, schema, CI workflow or compatibility-mode change.

## Background

`validate_candidate_scope()` currently checks `git diff B..C` only. A forbidden change followed by a restore can disappear from that overlay while remaining in the committed ancestry. The existing controller uses this function before trusted qualification. Earlier candidates 3eb21f194c91d06f62b2310021205a219485e565 and ac5f185004ee94195b9d914c951328b67c71a770 did not attach. Candidate 3cb160598991b75cdc8542eb4350a696cd12c023 was pushed, but its controller state had already advanced on planning-only qualification. Candidate e43b856e88c4e4b570cf8b0450d8baa6072dcd27 was rejected at attachment because its capsule revision differed from the external authorization revision. These attempts remain preserved; this capsule matches authorization revision three and uses separate planning and candidate state.
