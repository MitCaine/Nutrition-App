# E4-03-C1 — Restore row-scoped PostgreSQL Log locking after E4-03

## Goal

Correct the E4-03 PostgreSQL locking regression that made the generic Daily Log row-lock primitive acquire the owner `User` row and therefore serialized otherwise independent Daily Log updates for the same owner, without weakening E4-03 Complete invalidation under legacy/no-revision compatibility mutations.

## Outcome

`LogRepository.get_for_update()` is row-scoped again. Daily Log update/delete requests that carry authoritative `calendar_revision` acquire CalendarService's exclusive owner authority before their Log/date locks. Legacy/no-revision update/delete requests instead acquire a shared owner-row lock before their individual Log row: peer legacy mutations can coexist, while mark-Complete and calendar mutations using the exclusive owner lock serialize against them. Existing Complete invalidation behavior and public contracts remain unchanged.

## Non-goals

- No change to Complete persistence, request/status/recovery semantics, or invalidation matrix.
- No weakening or removal of the existing different-Log-row PostgreSQL concurrency contract.
- No schema, migration, API, mobile, UI, History, transfer, backup, synchronization, or capability changes.
- No redesign of the calendar authority model.

## Background

E4-03 aligned Log mutation ordering with E4-02 mark-Complete by moving an owner-row `FOR UPDATE` lock into `LogRepository.get_for_update()`. That generic helper is also the established row-level serialization primitive for unrelated Daily Log edits. The change therefore broadened lock scope from one Log row to every Log row owned by the same user. The existing PostgreSQL contract `test_different_log_row_does_not_wait` requires a second Daily Log row for the same owner to remain independently mutable, so the broad exclusive owner lock is a regression.

The first correction restored row-scoped `get_for_update()` and limited date-anchor locking to calendar-revision mutations. PostgreSQL CI then returned to 69/69 and E4-03 specialized qualification remained 6/6. Independent review identified one remaining untested boundary: a legacy/no-revision nutrition mutation still has to serialize against `mark_complete()` or a Complete assertion can race around its invalidation. The correction therefore uses a shared owner-row lock for no-revision update/delete. PostgreSQL permits concurrent shared locks on the same row, while `FOR UPDATE` conflicts with `FOR SHARE`; this preserves different-Log concurrency while retaining one owner-ordering boundary against Complete/calendar mutations.

Create is unchanged. With `calendar_revision`, it already acquires CalendarService's exclusive owner lock before the date anchor. Without a revision, it retains the E4-03 date anchor and never later acquires an owner lock, so it already serializes correctly with Complete without introducing an owner/date cycle.

## Owned surface

- Keep the owner-wide exclusive lock out of the generic `LogRepository.get_for_update()` row-lock primitive.
- Add a narrow shared owner-row lock helper for legacy/no-revision Log mutation ordering.
- Keep early CalendarService exclusive owner acquisition in `LogService.update_log()` and `LogService.delete_log()` when `calendar_revision` is supplied.
- Use the shared owner lock before the target Log row for no-revision update/delete.
- Reuse existing PostgreSQL concurrency tests and add narrow legacy-vs-Complete race coverage.

## Allowed changes

- A non-locking pre-read of the owned Daily Log may be used before authoritative update calendar validation solely to determine the candidate destination date; the later locked read remains authoritative for stale/precondition and mutation behavior.
- A repository helper may select the owner `User` row with a PostgreSQL shared row lock (`FOR SHARE`, expressed through SQLAlchemy's supported `with_for_update(read=True)` API); it must not commit or mutate the owner.
- Existing post-lock CalendarService validation remains in place as a fence against changed row/date state.
- Comments may be updated to accurately describe conditional owner ordering.

## Decisions and assumptions

- The generic Daily Log row-lock primitive must remain row-scoped; owner ordering is a caller-level concern.
- Authoritative calendar mutations use the existing exclusive owner lock. Legacy/no-revision update/delete use a shared owner lock so peer Log mutations do not serialize but mark-Complete/calendar `FOR UPDATE` does serialize against them.
- Update with a revision may perform a non-locking owned pre-read only to choose the candidate date for early calendar validation; all mutation/precondition decisions remain based on the later locked row and are revalidated before commit.
- Delete needs no date pre-read for early exclusive owner acquisition because existing `validate_delete_context()` is revision-only.
- Legacy create retains its existing date-anchor serialization and does not acquire an owner lock after the date anchor.
- Capsule revision 2 records the user-provided strict execution-preflight PASS and transition to bounded correction; product scope and ownership are unchanged.
- Capsule revision 3 records the independent-review discovery that legacy/no-revision update/delete also need Complete serialization, and bounds the repair to a compatible shared owner-row lock plus direct PostgreSQL race tests.
- Capsule revision 4 records final qualification and independent PASS review of `9c28d875d2afc95e571d9d24991ba178a7317fad`; no application behavior changed in this bookkeeping revision.
