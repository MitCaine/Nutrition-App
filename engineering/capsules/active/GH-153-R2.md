# GH-153-R2 — Complete remote response validation with Food error compatibility

## Goal

Complete issue #153's remaining remote-response validation using the exact
23-path candidate preserved by cancelled successor GH-153-R1, while explicitly
preserving the pre-GH-153 Saved Foods error-message compatibility surface that
R1 proved was lost by the strict Food parser.

## Outcome

All 28 response operations selected by GH-153 fail closed against canonical
backend contracts, while the existing Food source and recent-timestamp failure
semantics remain observably compatible.

Malformed successful Food responses must remain Zod validation failures so the
existing remote runtime continues to classify them as `invalid_response`.
Restoring compatibility must not replace Zod failures with generic errors.

Together with the 14 previously validated operations and two intentional
no-response-body delete operations, all 44 supported remote operations retain an
explicit response disposition.

The still-pending remote-isolation baseline fixture becomes canonical without
changing its network topology or local-authority isolation assertions.

- No change to Saved Foods product expectations.
- No change to remote-isolation request count, request order, methods, URLs, or

## Background

GH-153 created the strict capability-local response-validation implementation but
was cancelled when its required full mobile baseline exposed a remote-isolation
fixture outside its qualified post-READY scope.

GH-153-R1 freshly qualified that fixture scope, entered execution, and recovered
the predecessor's exact 22-path candidate. R1 then canonicalized the successful
Saved Foods wire fixtures, producing a 23-path candidate.

The canonical fixture repair succeeded for the positive Saved Foods behavior:
four of six tests passed. The two remaining failures proved a separate semantic
compatibility issue. The strict Food parser correctly rejects invalid source
data, but raw Zod messages replaced the pre-GH-153
`Invalid Food source contract` error surface. The timestamp compatibility
assertion was not reached in that failed test sequence, while pre-GH-153 source
proves `Invalid recent Food timestamp` was also an established observable
message.

Correcting those semantics requires a production edit inside the already-owned
Food API/schema surface. R1 explicitly prohibited semantic production edits in
its recovery and fixture-repair packages, so it terminated rather than widening
post-READY authority.

R1 was cancelled at exact commit `0c531f6e776d08082a4401e92199754372852af3`, tree
`4fc86b6364f225ddc4fbf7238d1a83ea28bb47b0`, with completed capsule blob `8294f7ee015519ad6d842ec95d14beef24a88fa5`.

Its exact 23-path candidate is frozen in stash `f789edb1c1de4b5d7de700b38da492572b08481a`. That candidate
already includes the canonical Saved Foods fixture repair.

The original 22-path predecessor candidate remains separately preserved in stash
`886e5343c77a9234419b95fccb925454f4f0ed39` as secondary evidence only.
