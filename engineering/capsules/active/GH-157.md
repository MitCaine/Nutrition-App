# GH-157 — Document canonical local iOS rebuild and launch commands

## Goal

Give contributors one canonical, unambiguous set of local-first iOS commands for
resetting/rebuilding, rebuilding without intentionally deleting installed data,
and relaunching already-installed development builds without unnecessary native
recompilation.

## Outcome

The root README distinguishes the common local-iOS development workflows and
makes clear when Metro alone is sufficient versus when native regeneration or
recompilation is required. Physical-device development and self-contained
Release installation remain distinct, and preserved PostgreSQL guidance retains
its protected migration boundary.

## Non-goals

- Application, runtime, native-module, generated iOS, schema, migration, Compose,
  dependency, script, toolchain, or release-version changes.
- Changing local/remote authority semantics.
- Creating a convenience PostgreSQL destructive-reset or direct-to-head upgrade
  workflow.
- Reworking iOS signing, native qualification, or release behavior.
- Adding repository scripts merely to shorten documented commands.

## Background

Version 2.0 is local-first, with authoritative application data stored in
on-device SQLite. The README currently documents normal Metro startup and a
self-contained physical-iPhone Release build, but it does not clearly separate
JavaScript/TypeScript-only iteration from workflows that actually require native
regeneration or recompilation.

Issue #157 requires canonical commands for five reader-visible cases:

1. destructive simulator reset/rebuild;
2. native simulator rebuild without intentionally deleting installed app data;
3. simulator launch of an already-installed development build without rebuild;
4. physical-iPhone launch of an already-installed signed development build
   without rebuild; and
5. the existing self-contained physical-iPhone Release install.

The bundle identifier is `com.portfolio.nutritionapp`. Generated
`apps/mobile/ios/` is intentionally ignored.

The preserved FastAPI/PostgreSQL runtime remains an alternate/reference
authority. Current remote startup requires a database already qualified at
`0033_complete_runtime_authority`; `0021_target_activation_execution` remains a
runbook-controlled operations boundary.

## Authority and precedence

1. Current repository configuration and installed command/tool interfaces.
2. `README.md`.

## Decisions and assumptions

- This is a low-risk documentation task because no runtime or generated-native
  state may change.
- The five workflows required by issue #157 should be independently visible
  rather than compressed into one ambiguous rebuild recipe.
- `npm ci` remains appropriate for initial setup and dependency reconciliation,
  not routine source iteration.
- JS/TS-only development should not imply native recompilation when an
  appropriate native development build is already installed.
- Simulator reset is intentionally destructive to the app sandbox; native
  rebuild is a separate workflow specifically because it should not
  intentionally clear installed application data.
- The existing physical Release installation remains self-contained and should
  not be rewritten as a Metro-based development workflow.
- PostgreSQL provisioning/progression is outside this task; the documentation
  must preserve the current qualified-database prerequisite and protected
  operations boundary.
