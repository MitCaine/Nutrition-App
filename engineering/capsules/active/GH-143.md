# GH-143 — Batch local Daily Log source-state reads

## Goal

Eliminate N+1-style current source-state reads from local Daily Log `list` and `listFuture`
without changing Daily Log behavior, historical authority, owner isolation, or ordering.

## Outcome

Each non-empty list invocation loads distinct owner-local source Foods in one bounded batch, then
loads the distinct owner-local Recipes and active publication revisions needed to classify those
Foods in one batch per source class. Each Log is mapped in its existing order from a per-call
source-state map. The existing singular source-state loader remains available to mutation and edit
flows.

## Non-goals

- No persistent or cross-call cache, synchronization, invalidation system, second authority, or
  background refresh.
- No backend, remote runtime, shared contract, SQLite schema/index/migration, dependency, transfer,
  UI, React Query, native boundary, or GitHub Actions change.
- No Daily Log mutation, Complete, snapshot replacement, Recipe publication write, or edit-context
  optimization.
- No batching of historical Recipe revisions that the existing list path does not read.

## Background

The current local `list` and `listFuture` paths read the owner profile and matching Logs, then call
`logResponse` for every row. `logResponse` calls the singular `loadSourceState`: one owner-scoped
Food read per Log, plus owner-scoped Recipe and active-revision reads for Recipe-marked Foods.
Issue #143 requires actual pre-change SQLite operation measurements rather than relying on the
audit estimate of roughly `2 + N` ordinary or `2 + 3N` Recipe-backed reads.
