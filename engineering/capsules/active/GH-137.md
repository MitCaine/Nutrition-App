# GH-137 — Prevent project shutdown from signaling recycled PIDs

## Goal

Prevent `scripts/stop-project.sh` from sending TERM or KILL to an unrelated process when a stale
project PID record refers to a PID that has since been recycled.

## Outcome

Project startup records enough process identity to distinguish the process it launched from a later
process using the same numeric PID. Project shutdown verifies that identity before signaling the
recorded root process, bounds descendant shutdown to the verified process tree, and revalidates
identity before forced termination.

Malformed, obsolete, exited, or identity-mismatched records fail closed and cannot authorize a
signal.

## Non-goals

- Redesign backend, Expo, Simulator, or Docker startup architecture.
- Change FastAPI, PostgreSQL, SQLite, NutritionRuntime, mobile runtime, or product behavior.
- Replace the current process-tree shutdown model with broad name-based process killing.
- Introduce an unverified process-group kill merely for implementation convenience.
- Modify `scripts/start-backend.sh` to avoid its existing shell-to-Uvicorn `exec` transition.
- Add a general-purpose daemon/process supervisor.
- Broaden this task into unrelated development-tool cleanup.

## Background

GitHub issue #137 records the project-wide audit finding that the current lifecycle scripts persist
only numeric PIDs. `stop-project.sh` accepts a numeric PID when `kill -0` succeeds, recursively
enumerates descendants by PPID, and then sends TERM followed by KILL after the existing grace
period.

That contract cannot distinguish the originally launched process from an unrelated process that
later reuses the same PID.

The backend root has an additional legitimate lifecycle property that the repair must preserve:
`start-project.sh` initially launches `scripts/start-backend.sh`, and that script later uses `exec`
to replace its shell process with the Uvicorn Python process without changing the PID. Expected
command validation therefore must recognize the bounded backend command transition rather than
requiring the initial argv to remain byte-for-byte unchanged.

The local project launcher is explicitly a macOS/Xcode development entry point. Process inspection
used as shutdown authority must therefore be proven on that supported host rather than assumed from
Linux-only behavior.

## Acceptance criteria

- [x] AC-1: Newly started backend and Expo roots are represented by a versioned process record that
  contains the numeric PID, a stable process-start identity, and an expected service command
  identity sufficient to reject an unrelated process using the same PID.
- [x] AC-2: A live PID whose start identity does not match its record is classified as stale or
  unowned and receives no TERM, KILL, or descendant signal.
- [x] AC-3: A live PID whose command identity does not satisfy its recorded service contract is
  classified as stale or unowned and receives no signal.
- [x] AC-4: Legacy one-line PID files, malformed records, and already-exited recorded processes
  cannot authorize signaling and are handled as stale local runtime state with an explicit
  diagnostic.
- [x] AC-5: The legitimate backend transition from `start-backend.sh` to
  `python -m uvicorn app.main:app` remains recognized as the same project-owned backend root when
  PID and start identity are unchanged.
- [x] AC-6: Normal shutdown still terminates the verified backend/Expo root and its disposable
  descendant process tree without signaling processes outside that tree.
- [x] AC-7: The existing graceful timeout remains intact; before any forced KILL, process start
  identity is revalidated so a PID that exited and was recycled during the wait cannot be killed.
- [x] AC-8: Descendant shutdown captures and verifies sufficient child identity to prevent a
  child PID that exits and is recycled during shutdown from receiving a later forced signal.
- [x] AC-9: Startup recognizes a matching live process record as already running, while an exited
  or mismatched record does not become authority for a different live process.
- [x] AC-10: The process-inspection fields and assumptions used for ownership are documented and
  directly qualified on macOS; focused tests remain runnable in ordinary repository CI where the
  underlying `ps` contract is compatible.
- [x] AC-11: No backend/mobile product code, database authority, schema, migration, runtime
  selection, or application-data behavior changes.
