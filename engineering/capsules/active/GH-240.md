# GH-240 — Make attached versus compatibility workflow mode explicit

## Goal

Close the implicit unattached path that lets a new task bypass its capsule and candidate-evidence stages.

## Outcome

New tasks have an authenticated, explicit attached workflow mode by default. A compatibility exception requires a recorded owner-authorized reason, while already authenticated legacy states retain their established route.

## Non-goals

- No retroactive capsule or evidence obligations for sealed legacy work.
- No changes to authorization-v1 path/profile semantics, application code, profile registry, or GitHub workflows.

## Background

The base controller chooses the attached path by checking for `capsule_evidence` in mutable state. Issue #240 requires an authenticated explicit mode and preservation of old state. Revision-one C `166141b3816ac593af4f3197d7b27c0787076ee6` remains preserved after its RI structural capture exceeded the 2 MB artifact cap. Its review and `STOP_REPLAN` state remain preserved; no approval or integration is inferred.
