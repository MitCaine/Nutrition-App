# GH-132-P1 — Establish semantic color foundation

## Goal

Establish one reusable light/dark semantic color vocabulary for GH-132 so
later visual-polish slices can differentiate major features and nutrition data
without accumulating one-off colors or turning nutrition intake into
red/green pass-fail scoring.

## Outcome

P1 adds exactly 14 semantic color roles to the shared application theme:

Feature identity:

- `dailyLogForeground`
- `dailyLogBackground`
- `foodsForeground`
- `foodsBackground`
- `recipesForeground`
- `recipesBackground`
- `historyForeground`
- `historyBackground`

Encouragement:

- `encouragementForeground`
- `encouragementBackground`

Nutrition-series identity:

- `nutritionCaloriesSeries`
- `nutritionProteinSeries`
- `nutritionCarbohydrateSeries`
- `nutritionFatSeries`

Both light and dark themes expose the same 49 total color roles after P1.
The existing 35 roles and their values remain unchanged.

The new roles are defined and mechanically qualified but deliberately unused by
feature screens in P1, so P1 produces no visible application change.

## Non-goals

- Recoloring bottom navigation.
- Recoloring Foods, Daily Log, Recipes, History, or Daily Nutrition screens.
- Changing chart rendering or chart-selection geometry.
- Adding the future non-color selected-chart marker.
- Migrating the 19 existing hard-coded camera/diagnostic/bootstrap/transfer
  colors identified during discovery.
- Changing existing action, success, warning, error, destructive, surface,
  input, navigation, disabled, or status semantics.
- Using color to classify nutrition intake as good/bad, success/failure,
  adherent/non-adherent, or healthy/unhealthy.
- Backend, persistence, API, runtime-authority, migration, or calculation
  changes.
- Physical light/dark or color-vision-deficiency qualification; those begin
  when later GH-132 slices actually consume the tokens.

## Background

GitHub issue #132 identifies an increasingly mechanical blue/gray mobile
appearance and requests a richer theme-level semantic/accent system while
preserving contrast, non-color cues, and the rule against red/green nutrition
grading.

Fresh discovery on exact base
`9108a7cb03783cfe8cac35da9f621bef6907b635` found:

- 35 existing semantic color roles;
- `accent` is referenced 67 times across 28 files and currently carries too
  many unrelated visual meanings;
- the existing light primary-action blue is `#1f6fb2`;
- exactly 19 hard-coded colors exist outside `AppTheme.tsx`, concentrated in
  five OCR or pre-theme runtime/transfer files and explicitly outside P1;
- the only active non-README capsule on exact main is blocked
  `WF-003-implementation-result-artifacts`, whose own forbidden surface
  includes `apps/mobile/**`, so it has no P1 ownership conflict;
- current `appTheme.test.ts` baseline is 10/10 passing;
- current mobile TypeScript typecheck passes.

The initial candidate reused `#dbeafe` as the light Daily Log tint, but
discovery correctly rejected its 4.33:1 foreground/tint contrast. The
corrected tint `#eaf3fb` yields 4.71:1 while preserving the established
`#1f6fb2` foreground.

## Decisions and assumptions

- Existing blue remains the universal action language.
- Daily Log feature identity uses established blue.
- Foods uses teal.
- Recipes uses violet/plum.
- History uses indigo.
- Encouragement uses green-blue/teal and is not operation success.
- Calories use blue, Protein teal, Carbohydrate amber, and Fat violet for stable
  category identity only.
- Nutrition-series colors do not encode quality or adherence.
- The corrected light Daily Log tint is `#eaf3fb`; rejected
  `#dbeafe` remains an existing legacy token value only and is not reused for
  the new Daily Log tint.
- The 19 hard-coded OCR/runtime/transfer colors are classified but deferred.
- WF-003 is blocked and non-conflicting.
- P1 is deliberately token-only. Visible design application begins with P2.
- No material assumption remains unresolved.
