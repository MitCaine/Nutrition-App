# GH-159-R1 — Resume Version 2.0 documentation reconciliation with complete audit-test scope

## Goal

Create a documentation hierarchy in which current Version 2.0.0 behavior and repository operation
have clear canonical owners, completed planning and release records are visibly historical without
losing provenance, and the engineering workflow has one coherent post-GH-158 lifecycle contract.

## Outcome

Three sequential documentation passes are completed and independently validated on one branch:

1. completed planning, release, and implementation-provenance records move into the existing
   historical hierarchy with repaired navigation and no duplicate authority;
2. current product, architecture, feature, reference, and operations documents accurately and
   concisely describe Version 2.0.0 from current executable authority; and
3. engineering/process documentation consistently describes the active-capsule to `HISTORY.md`
   terminal model while preserving dated workflow evidence and any human policy boundary.

## Non-goals

- Changing application runtime behavior, APIs, persistence semantics, schemas, migrations,
  database/control authority, synchronization, fallback, dual-write, recovery policy, or product policy.
- Mechanically replacing historical version numbers, migration heads, issue states, commit IDs,
  architecture decisions, or release assertions with current values.
- Claiming tags, GitHub Releases, App Store publication, platform parity, public multi-user support,
  or other release events without direct Git/GitHub/implementation evidence.
- Formally promoting Workflow v3 without explicit human-approved policy authority.
- Collapsing distinct feature domains or creating a new permanent audit/archive index without a
  demonstrated authority gap.
- Broad validator or application-test refactoring unrelated to legitimate documentation moves.

## Background

GH-158/R1 replaced per-task completed capsule files with a durable terminal history index. The
repository now identifies itself as Version 2.0.0, while its documentation contains a mixture of
current guidance, deliberately pinned operational boundaries, completed Version 1.x programs, and
point-in-time evidence. These roles must be separated without retroactively rewriting history.

The predecessor GH-159 execution reached IN_PROGRESS but changed no documentation files. It was cancelled when the path-sensitive project-audit regression test was found to be required but absent from machine-readable scope. GH-159-R1 preserves the same issue objective with that exact test path now admitted.

## Authority and precedence

1. Current implementation, migrations, executable tests, scripts, and verified Git/GitHub state.
2. Root `VERSION` and canonical repository metadata.
3. Current State plus current architecture, feature, reference, and operations guides.
4. Accepted architecture decisions and invariants.
5. Completed versioned planning/release records and other historical evidence.
6. GitHub issue #159 and this execution capsule coordinate the bounded maintenance work.
7. Assumptions.

## Allowed changes

- Move completed Version 1.x program/release/chronology records into the existing historical hierarchy.
- Repair internal and inbound links, indexes, navigation, anchors, and path-sensitive validation.
- Create one compact current PostgreSQL-to-SQLite transfer/compatibility guide only if implementation
  and tests prove the capability remains supported.
- Reconcile current prose against current executable and verified external authority.
- Consolidate duplicate current authority while preserving deliberately distinct document roles.
- Align engineering/process guidance with the post-GH-158 active/HISTORY lifecycle.
- Add a dated workflow changelog entry if needed to preserve later evidence without rewriting history.
- Update focused validator tests only when path/lifecycle documentation changes require coverage.
- Update `apps/backend/tests/test_project_audit.py` only where legitimate documentation moves require its path-sensitive current-document contract expectations to change.

## Forbidden changes

- Runtime, API, application, schema, migration, database, persistence, dependency, toolchain, CI,
  or product-policy changes.
- Rewriting historical statements merely because current implementation is newer.
- Weakening validators or qualification to make documentation pass.
- Moving an executable current runbook into history when doing so would weaken operational authority.
- Changing frozen 0020/0021 operational boundaries into the 0033 application head.
- Creating sync, fallback, dual-write, shared-cache, cloud-backup, or unsupported platform claims.
- Formal Workflow v3 promotion without explicit human-approved authority.
