# E4-01 — Add date-owned Complete persistence for local and remote authorities

## Goal

Introduce the minimum durable persistence substrate for Epic 4 day-level `Complete` assertions in both selected application-data authorities while preserving existing Daily Log history and authority isolation.

## Outcome

Remote PostgreSQL and local SQLite each have one positive, date-owned Complete-state representation with internal completion-time evidence; repository/service storage operations can read and assert that state, empty dates are rejected at the service boundary, existing dates are not backfilled, and no user-facing or HTTP Complete mutation is introduced.

## Non-goals

- Complete UI, History UI, or Daily Nutrition UI.
- Public HTTP mark-Complete mutation or deterministic mutation receipt/reconciliation behavior; E4-02 owns that work.
- Automatic Complete invalidation from create/edit/delete/move; E4-03 owns that work.
- Manual un-completion.
- Bounded History range reads or History calculations.
- Backup/restore or one-time transfer propagation; E4-15 owns that work.

## Background

Epic 4 separates logging coverage from nutrient-data completeness. A Complete assertion describes whether the user believes all food for one authoritative Daily Log calendar date was logged. It therefore belongs to the date, not to any individual Daily Log entry, and must not modify immutable nutrient snapshots. Local SQLite remains the normal authority and remote FastAPI/PostgreSQL remains the preserved alternate authority; this task adds equivalent persistence semantics without synchronization or a new runtime capability.

- E4-01 may expose repository/service/local-storage functions needed for later tasks but must not expose a new user-facing/HTTP Complete mutation contract.
- Current migration-head documentation and repository-generated migration-head inventory may be updated mechanically in this task because repository audit must describe the actual new head; broader feature documentation remains E4-17 work.
