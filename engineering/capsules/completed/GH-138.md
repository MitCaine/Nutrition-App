# GH-138 — Align remote Target current date to owner calendar authority

## Goal

Remove host-local calendar date from remote Target reads and mutations so current Target calculations
use the same owner-scoped calendar authority as the local SQLite runtime.

## Outcome

Remote Target configuration reads, updates, and override resets derive one effective Target date from
the authenticated owner's authoritative IANA time zone. When a legacy/pre-calendar profile genuinely
has no established time zone, the fallback is explicit UTC rather than backend-host local time.

Current Target mutations resolve that date inside the existing serialized owner mutation boundary,
so a concurrent calendar change cannot leave age-sensitive validation or returned recommendations
using stale calendar authority.

Historical/selected-date Target comparison remains explicitly keyed to its requested Daily Log date.

## Non-goals

- Change DRI datasets, recommendation tables, maintenance-calorie equations, Target precedence, or
  Target direction semantics.
- Change persisted Target, profile, calendar, or Daily Log schemas.
- Require calendar establishment before legacy/pre-calendar Target configuration can be read.
- Change `/api/v1/targets/daily-comparison` from selected-date semantics to current-date semantics.
- Change local SQLite Target behavior.
- Add synchronization, fallback between local and remote authorities, dual write, or mixed authority.
- Change calendar establishment/change semantics.
- Rework Target UI or Target response schemas.
- Broaden into general clock abstraction or time-zone cleanup outside current Target calculations.

## Background

GitHub issue #138 records a project-wide audit finding: the remote Target router currently calls
Python `date.today()` for current configuration GET, configuration PUT, and manual-override DELETE.

Those dates flow into `TargetService`, where they control birth-date validation, age-sensitive
maintenance estimates, DRI selection, effective Targets, and the configuration returned after a
mutation.

The backend already has authoritative calendar infrastructure. `CalendarService.state()` derives
`today` from the persisted owner `authoritative_time_zone`, and `CalendarService.today_in_zone()`
performs the IANA-zone conversion from an aware UTC instant.

The local SQLite Target runtime already has the intended compatibility rule. Its Target-date helper
uses the persisted authoritative time zone when present and otherwise uses UTC as the deterministic
pre-calendar fallback.

One concurrency detail prevents this from being only a router substitution. Target mutations use a
User-first `FOR UPDATE` lock before profile/Target mutation. Calendar establishment deliberately
uses the same User-first order. A current Target mutation must therefore acquire that owner lock
before resolving the current Target date; otherwise a calendar change that wins the lock could
commit while the Target request continues using an earlier calendar observation.

`/api/v1/targets/daily-comparison` is different: its requested Daily Log date is intentionally the
`as_of` date and must remain so.

task. Backend host-local date is not authority.

Stop and return to the controller if:

- satisfying current Target date authority requires changing `CalendarService` semantics;
- the pre-calendar fallback cannot remain deterministic UTC without changing an established public
  contract;
- current Target mutation date cannot be resolved after the existing User owner lock without
  changing lock order or introducing a second lock authority;
- implementation requires a database migration, persisted date field, calendar revision change, or
  new Target state;
- `/daily-comparison` would need current-date semantics rather than its explicit selected date;
- local SQLite executable Target behavior would need to change rather than merely be qualified;
- a shared parity fixture exposes an existing local/remote recommendation-rule mismatch unrelated to
  date authority;

- implementation needs any path outside owned/allowed scope.
