# E4-05 — Implement one shared History calculation/projection layer

## Goal

Add one pure shared History projection layer over the E4-04 `HistoryRangeEvidence` contract so Complete-day/Logged-day averages, coverage, nutrient-specific usable-day counts, daily chart values/gaps, exact selected-date values, and grouped Nutrition Details rows all derive from one semantic implementation independent of the selected storage authority.

## Outcome

Equivalent local SQLite and remote FastAPI/PostgreSQL range evidence is interpreted by the same mobile/domain calculation code. The projection preserves exact decimal values and evidence provenance, exposes deterministic Complete-day and Logged-day denominator results, retains gaps/unavailable states instead of inventing zero, and provides the full canonical nutrient-row structure through the existing nutrient catalog/taxonomy while keeping absent evidence unavailable. No authoritative fetch, new API, backend calculation path, cache policy, target-history model, or History UI is added.

## Non-goals

- No new or changed backend endpoint, service, repository, schema, or test path.
- No changes to E4-04 range retrieval, runtime delegation, authority selection, error mapping, or evidence persistence semantics.
- No React Query identity/cache invalidation/latest-request-wins work; E4-06 owns those behaviors.
- No History route, range controls, charts, sheets, or focused-nutrient UI; E4-09 through E4-12 own presentation.
- No current Target/reference retrieval or historical Target reconstruction.
- No coaching, trend judgement, prior-period comparison, goal grading, or adherence scoring.
- No display rounding authority; E4-05 returns exact projection values and downstream presentation applies canonical display precision.

## Background

E4-04 established one authority-scoped evidence read with per-date `hasLogs`, `isComplete`, exact known/estimated amounts, explicit-zero semantics, unknown-contributor metadata, and no-Log gaps. Epic 4 requires interpretation of that evidence to live in one shared layer rather than independently in SQLite and FastAPI/PostgreSQL.

The repository already provides `ResponseDecimal` arithmetic using BigInt-backed decimal text and Python-Decimal-compatible 28-digit ROUND_HALF_EVEN context, plus the canonical nutrient catalog and section grouping. E4-05 should compose those authorities rather than introduce floating-point arithmetic, a second nutrient taxonomy, or server-specific average semantics.

The Feature PRD also requires every canonical Nutrition Details nutrient row to remain structurally available even when the selected range has no usable value. Structural row availability is not synthesized nutritional evidence: absent nutrient evidence remains unavailable with no numeric value and never contributes to an average.

## Allowed changes

- Add a projection mode equivalent to `complete_days | logged_days` that changes only deterministic denominator interpretation over the same `HistoryRangeEvidence`.
- Calculate exact daily numeric amount as `amountKnown + amountEstimated` only when `hasNumericEvidence=true`.
- Complete-day average eligibility requires `day.isComplete` and selected-nutrient usable numeric evidence.
- Logged-day average eligibility requires `day.hasLogs` and selected-nutrient usable numeric evidence.
- Exclude no-Log dates and unknown-only/absent selected-nutrient dates from numeric denominators without converting them to zero.
- Include explicit-zero evidence as a usable zero observation in the denominator.
- Preserve exact known and estimated components in projected daily evidence so estimated provenance is not erased when calculating the combined numeric value.
- Preserve unknown-contributor and explicit-zero metadata on daily projected values.
- Sum exact response decimals across eligible days before dividing once by the actual usable-day count; do not round individual days.
- Return exact derived average text; do not perform display formatting/rounding inside this task.
- Derive range-level coverage counts from the same evidence: requested dates, logged dates, and Complete dates.
- Derive nutrient-specific usable-day counts and average denominators from the same daily projected values.
- Derive deterministic daily chart/selected-date states equivalent to numeric, unavailable/unknown-only, and no-Log gap; do not manufacture numeric zero for unavailable states.
- Create one structural projection row for every nutrient in the existing canonical nutrient catalog. If a nutrient is absent from E4-04 evidence for the entire range, its logged dates remain unavailable, no-Log dates remain gaps, `usableDayCount` is zero, and `average` is null.
- Structural canonical rows must not manufacture nutritional evidence or parent totals. Child evidence never produces a numeric parent value unless parent evidence itself exists.
- Use the catalog's canonical default unit for structurally absent rows. Observed evidence for a canonical nutrient must use that same canonical unit; contradictory evidence units fail explicitly rather than being silently combined.
- Group all canonical structural rows with the existing canonical nutrient section/order helper; no second nutrient taxonomy or ordering table is introduced.
- Add a shared fixture containing representative E4-04 evidence plus exact expected projections for Complete-day and Logged-day modes.

## Decisions and assumptions

- E4-05 calculates exact projection values; presentation-specific decimal-place rounding remains downstream.
- `usableDayCount` is nutrient-specific and is the actual denominator used for that nutrient/mode, not a range-wide logged/Complete count.
- `coverage` is range-wide evidence metadata (`requestedDayCount`, `loggedDayCount`, `completeDayCount`) and is distinct from nutrient-specific `usableDayCount`.
- Daily projection retains `amountKnown` and `amountEstimated` separately and also exposes their exact numeric sum when usable; this preserves the E4-04 provenance that is actually represented by the frozen evidence contract.
- A numeric value with unknown contributors remains usable and carries uncertainty metadata; unknown contributors do not automatically remove the day from the denominator.
- A logged date where a nutrient item is absent is unavailable for that nutrient and differs from an explicit unknown item only in retained evidence detail; neither enters a numeric denominator.
- A no-Log date is a chart gap and never becomes a zero observation.
- `average = null` (or semantic equivalent) when `usableDayCount = 0`; zero is reserved for a real usable zero result.
- Canonical structural rows come from the existing nutrient catalog solely to satisfy History information structure. They do not create or imply historical nutrient evidence; absent evidence remains unavailable and contributes no numeric value.
- Equivalent local/remote projection means the pure layer contains no selected-authority branching; authority identity remains an E4-04/E4-06 concern.
