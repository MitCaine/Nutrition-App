# E4-06 — Add History query identity, cache invalidation, and stale-response protection

## Goal

Add one authority-local React Query ownership layer for E4-04 History range evidence so exact range identity, stale-response protection, same-range refresh behavior, and mutation-driven invalidation remain deterministic without changing the underlying authority read or E4-05 projection semantics.

## Outcome

History range reads are cached only under the selected authority identity and exact inclusive LocalDate bounds. Switching 7/30-day windows, paging, or changing authority selects a different evidence entry rather than reusing another range's payload. A late request for an old key cannot become current visible data. Successful Daily Log and Complete mutations invalidate only cached History ranges in the same authority whose bounds contain affected dates. Same-range refresh failure may retain same-range evidence with explicit error/retry state, while a failed new-range request never displays a different range's cached payload. No persistent History cache, synchronization, backend work, projection arithmetic change, or History UI is added.

## Non-goals

- No new backend endpoint, repository/service calculation, schema, migration, or PostgreSQL behavior.
- No change to E4-04 `HistoryRangeEvidence`, `getHistoryRange`, local/remote delegation, authoritative LocalDate validation, or one-request remote contract.
- No change to E4-05 Complete/Logged denominator arithmetic, exact decimals, canonical nutrient structure, or presentation projection semantics.
- No History route, range controls, paging UI, charts, sheets, or focused-nutrient presentation; E4-09 through E4-12 own those surfaces.
- No persistent/offline History cache beyond the selected local authority's ordinary source data and React Query's in-memory process cache.
- No synchronization, replication, fallback, dual/shadow reads, mixed authority, or cross-authority cache reuse.
- No target/reference application to historical evidence and no invalidation of History evidence merely because current target/reference state changes.

## Background

E4-04 established one bounded raw History evidence read owned by the already-selected local or remote Daily Logs authority. E4-05 established one pure projection over that evidence. E4-06 owns the client query lifecycle between those layers: a cached result must remain attached to the authority and exact range that produced it, and authoritative mutations must invalidate every cached range whose evidence could now be stale.

The existing mobile logging hooks already use React Query and centralize successful Daily Log mutation refresh/invalidation in `useLogMutations()`. `NutritionRuntime.authority` already exposes the selected authority identity as `{ kind, recoveryScope }`. E4-06 should compose those existing ownership boundaries rather than introduce a second authority selector, persistent cache, or History-specific transport path.

## Dependencies and prerequisites

- E4-04 and E4-05 are merged and archived on `main`; exact E4-06 baseline is `94b551a1b3d4fb1746f24de0e43847516cad028b`.
- `runtime.dailyLogs.getHistoryRange(startDate, endDate)` already performs the one selected-authority evidence read.
- `runtime.authority.kind` and `runtime.authority.recoveryScope` already distinguish the selected runtime authority identity used for recovery/cache ownership.

## Owned surface

Implementation is limited to one History query/cache module, the existing Daily Log React Query mutation hook needed to connect authoritative mutations to History invalidation, and focused mobile tests. Runtime authority selection, E4-04 transport/storage, E4-05 projection math, targets, persistence, and presentation remain dependencies outside the owned surface.

## Allowed changes

- Define one stable History range query key whose identity includes a History namespace, selected `runtime.authority.kind`, selected `runtime.authority.recoveryScope`, exact inclusive `startDate`, and exact inclusive `endDate`.
- Keep raw E4-04 evidence as the cached query value; do not cache a second authority-specific aggregate or embed E4-05 projection mode in the evidence key.
- Add a History range query hook/helper that invokes exactly one `runtime.dailyLogs.getHistoryRange(startDate, endDate)` for its selected key and never falls back to another authority or range.
- Provide an explicit History read-state projection that distinguishes initial loading, initial/new-range failure, success, refreshing with same-range evidence, and refresh failure retaining only same-range evidence with retry.
- Rely on exact key isolation and React Query observer ownership so a late response for a previous range/authority may populate only its own cache key and cannot replace the currently selected query's visible evidence.
- Do not use cross-key placeholder/previous data that would display another range while a new range loads or fails.
- Add an authority-scoped invalidation helper that receives one or more affected canonical LocalDates and invalidates only History range queries for the same authority whose inclusive `[startDate, endDate]` contains at least one affected date.
- Treat inclusive start and end dates as affected-range members; de-duplicate repeated affected dates without broadening invalidation.
- Connect successful Daily Log create/delete/nutrition-changing update/move mutation paths in the existing logging hook to same-authority History invalidation for the authoritative affected date set. A move invalidates both source and destination ranges.
- Preserve existing E4-03 server/local Complete invalidation semantics: when a successful log mutation changes historical nutrition, the containing History range is invalidated so both nutrition evidence and `isComplete` are reread together rather than locally reconstructed.
- Expose a non-UI Complete mutation path or equivalent reusable success invalidation primitive for existing `markDayComplete()` so successful first assertion and reassertion invalidate same-authority History ranges containing that date; E4-07 owns rendering the control.
- Leave current target/reference changes outside History evidence invalidation; they are a separate current-reference lens.
- Add deterministic focused tests for query identity, range switching, authority switching, out-of-order requests, same-range refresh failure, new-range failure, inclusive targeted invalidation, Log mutation integration, and Complete success invalidation.

## Forbidden changes

- No backend/API/runtime implementation or interface changes, no SQLite queries/schema/migrations, and no second History evidence fetch path.
- No authority-specific local/remote History hooks or calculations; one shared query layer must consume the already-selected runtime.
- No key that omits authority identity or either exact range endpoint, and no cache fallback between authorities.
- No cross-range `placeholderData`, previous-range rendering, cache copying, or manual result assignment that can present a different range as current.
- No broad clearing of all React Query caches when exact same-authority/date-overlap invalidation is possible.
- No inferred local mutation of cached History numeric evidence or Complete state as a substitute for authoritative refetch.
- No target/reference state in the raw evidence key unless it changes the E4-04 evidence payload; current accepted contracts say it does not.
- No Complete UI, History screen/navigation, range controls, charts, or presentation work.
- No change to exact decimal, canonical nutrient catalog/grouping, E4-05 projection, or display rounding behavior.
- No persistent History cache, synchronization, background replication, fallback, mixed authority, dual/shadow reads, or ninth runtime capability.
- Do not modify frozen Epic 4 PRD/data-contract/architecture documents in this task.

## Decisions and assumptions

- The cached value is raw E4-04 `HistoryRangeEvidence`; E4-05 projection remains a pure downstream interpretation and may be recomputed without refetching evidence when Complete/Logged mode changes.
- `runtime.authority.kind` plus `runtime.authority.recoveryScope` is the existing runtime identity boundary available to React Query; E4-06 does not invent a second authority identifier.
- Start/end LocalDates are canonical E4-04 inputs and form inclusive evidence bounds. Range membership is date-based, not timestamp-based.
- Exact query-key separation is the primary stale-response guard: an old request may finish and populate its own cache entry but cannot become the current observer's result after the observer key changes.
- E4-06 intentionally avoids `placeholderData`/previous-range carryover so a new range never masquerades as already-loaded data from another range.
- Same-range refresh retention is permitted only because the retained payload has the identical authority/range identity; the state must still surface the refresh error and retry action.
- Target/reference values are a current comparison lens, not historical evidence. Their changes neither alter E4-04 payload identity nor invalidate raw History evidence.
- Successful log mutation invalidation is triggered only after authoritative mutation success; failed/indeterminate mutation handling remains governed by the existing Daily Logs recovery contract and must not fabricate History state.
- E4-07 owns the visible Complete control. E4-06 may add only the non-UI mutation/invalidation hook needed to make that future control cache-correct from its first use.
