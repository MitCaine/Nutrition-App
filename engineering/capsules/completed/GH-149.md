# GH-149 — Finish first-class Recipe reuse and discovery

## Goal

Finish first-class Recipe reuse and discovery by allowing valid current managed Recipe Food
projections to participate in the existing canonical Food-recency read path and by presenting
Recipe publication lifecycle and recent-use discovery in the Recipe UI.

Reuse existing authorities. Do not create Recipe-specific favorite, recent, ranking, or history
state.

## Outcome

When complete:

- canonical Food recents can return valid current managed Recipe projections in both remote and
  local runtimes;
- ordinary Food recency behavior and ordering remain intact;
- Recipe presentation clearly communicates whether a Recipe has never been published, is
  published/current, or needs republishing;
- users can discover recently used Recipes from the existing Food-recency authority;
- Recipe editing remains Recipe-side and published Food projections remain the reusable/loggable
  Food-side representation;
- managed Recipe projections remain non-favoritable under the existing contract.

## Non-goals

- Making managed Recipe Food projections favoritable.
- Creating Recipe-specific recent, ranking, usage, or history persistence.
- Creating another React Query or domain-data authority.
- Changing immutable Daily Log historical nutrition.
- Changing Recipe publication identity or revision semantics.
- Changing API response shapes.
- Changing transfer formats.
- Adding schema, SQLite migration, Alembic migration, or index work.
- Adding synchronization, fallback, dual-write, failover, or authority mixing.
- General Recipe redesign or unrelated UI polish.

## Background

GitHub issue GH-149 asks to finish Recipe reuse and discovery, including allowing Recipes to be
favorited and/or appear in recents and improving publication-state presentation.

Repository audit at the authoritative base found that the issue's baseline assumption is broader
than the current implementation:

- backend Food favorite/recent saved predicates exclude managed Recipe projections;
- local SQLite `FoodsRuntime.listRecent()` also excludes Recipe projections;
- managed Recipe projections are deliberately non-favoritable;
- Daily Log usage is already the canonical immutable source from which Food recency is derived.

The issue's "favorites and/or recent Foods" criterion can therefore be satisfied through canonical
Food recents without widening favorite mutation semantics.

Recipe detail already contains publication-aware behavior and existing Publish, Republish, and
View Published Food actions. The initial production scope therefore targets Recipe-list lifecycle
and discovery presentation. Recipe detail is outside the initial owned surface unless focused audit
proves a bounded change is necessary and the capsule is revised before implementation.

## Authority and precedence

Authority remains:

1. The owner-visible Recipe is authoritative for Recipe editing and publication state.
2. The current published Food projection is the reusable Food-side representation.
3. Immutable Daily Log usage/history remains authoritative for recency.
4. Canonical Food recent queries remain authoritative for recent-item ordering.
5. Existing Recipe publication revision relationships remain authoritative for determining whether
   a Recipe-managed Food projection is current and valid.
6. Existing favorite mutation rules remain authoritative; GH-149 does not widen them.

Where the issue description conflicts with the current repository, the audited repository contract
takes precedence unless this capsule explicitly authorizes a bounded change.

A Recipe-like Food row must not become valid discovery data merely because it carries a Recipe
marker or arbitrary source identifier.

  exact existing Publish/Republish, published-nutrition inspection, and Log Recipe actions.

A valid recent managed Recipe projection must preserve current managed-projection semantics,
including owner scope and current publication identity. The implementation should establish the
equivalent of:

- Food is not deleted;
- Food is Recipe-managed according to the existing managed-projection contract;
- Food has a publication revision identity;
- the same-owner Recipe exists and is not deleted;
- Recipe `published_food_item_id` identifies that Food;
- Recipe `active_publication_revision_id` matches the Food publication revision.

Prefer relationally established managed-projection validity over trusting arbitrary `Food.source_id`
data.

Backend and local recency qualification must exclude malformed, stale, deleted, inconsistent, or
cross-owner Recipe-like candidates before the canonical recent-result `LIMIT` is applied. A
post-limit presentation filter may remain as defense in depth, but invalid candidates must not
consume result slots.

Recipe-list discovery must map a qualified recent managed Food projection back to an owner-visible
Recipe through the Recipe's existing `published_food_item_id` relationship to the recent Food ID.
Presentation code must not treat arbitrary `Food.source_id` as its Recipe identity authority.
