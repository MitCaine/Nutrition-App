# GH-139 — Validate high-risk remote API responses before use

## Goal

Fail closed before application code dereferences malformed successful remote responses on the
highest-risk Daily Log immutable/history/Complete and Recipe publication surfaces.

## Outcome

The remote logging and Recipe API modules request `unknown`, validate complete successful response
objects through strict capability-local Zod schemas, and return the established application types
without changing valid-response behavior or exact decimal strings. Schema failures cross the
existing remote runtime boundary as non-retryable `invalid_response`; mutation response failures
retain unresolved outcome semantics.

## Non-goals

- No global response-validation framework or domain-specific behavior in generic `apiRequest`.
- No validation expansion to Recent Entries, edit context, Recipe duplication, Recipe nutrition,
  Foods, Targets, OCR, USDA, Calendar, UI, navigation, caching, or query behavior.
- No backend, API-version, migration, SQLite, transfer, dependency, synchronization, fallback,
  dual-write, shadow-write, or local-authority change.

## Background

Current generic `apiRequest` parses successful JSON and applies only a compile-time cast. Targets already request
`unknown`, validate strict Zod schemas, and then map established mobile types. The existing remote
error mapper classifies `ZodError` as `invalid_response`, non-retryable, with reads
`not_applicable` and mutations `unresolved`. GH-150 is integrated at the authoritative base and
Recipe duplication remains outside this task.

Reconnaissance selected the exact high-risk response seam: ordinary `DailyLog` responses returned
by list/future/create/update and nested in mutation-status recovery; History range; Complete and
nested completion recovery; and the adjacent Daily Summary immutable nutrient aggregate. The
separate Recent Entry and edit-context representations do not share these exact schemas and remain
out of scope. Recipe scope is only the complete publication result and its nested Recipe, ingredient,
managed Food, serving, and nutrient objects.

## Forbidden changes

- Do not add local/remote fallback, synchronization, shared mutable recovery authority, dual write,
  shadow write, or any second application-data authority.

  strings, nullable `first_logged_date`, booleans, finite nutrient units, non-negative integer

- [x] AC-3: Complete validates canonical `logged_date` and timestamp strings before return, both
  directly and when nested in mutation-status recovery.

  changing summary calculation or result shape.
- [x] AC-5: Recipe publication validates the full strict Recipe/ingredient and managed
  Food/serving/nutrient response trees before return without changing duplication or publication
  behavior.
- [x] AC-6: Exact numeric response values accept only bounded plain decimal strings, preserve the
  exact lexical string, and reject JSON numbers, exponents, signs, non-finite text, and arbitrary
  text; no string-to-number conversion occurs.

  required-field, and unexpected-field contracts fail closed; no unproven legacy shape is accepted.
- [x] AC-8: Malformed History reads become non-retryable `RuntimeError(kind=invalid_response,
  mutationOutcome=not_applicable)` through the actual remote runtime boundary.

  authority remains active with no fallback, synchronization, dual write, or local validation path.
