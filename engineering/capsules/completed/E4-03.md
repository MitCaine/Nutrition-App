# E4-03 — Atomically invalidate Complete on nutrition-changing Log mutations

## Goal

Guarantee that a positive date-owned Complete assertion cannot remain authoritative after a successful Daily Log mutation changes that date's logged nutrition, while preserving Complete for metadata-only changes and nutrition edits whose persisted nutrient snapshot generation is exactly unchanged.

## Outcome

Existing remote and local Daily Log create/update/delete operations clear affected Complete state inside the same authoritative transaction as the successful mutation. Moves clear both source and destination dates in that one transaction. Metadata-only note/meal edits preserve Complete. A serving/amount edit preserves Complete only when the resulting persisted nutrient snapshot set is exactly equivalent to the pre-mutation set; any actual stored snapshot change clears it. Mutation receipts/replay remain owned by the existing Daily Log mutation model, and no second cleanup write, API, runtime capability, schema change, or synchronization path is added.

## Non-goals

- No user-initiated clear/un-complete operation.
- No Complete UI, Daily Log layout work, History UI, History range reads, projections, averages, or charts.
- No changes to E4-02 Complete assertion request/result/status semantics or its recovery journal.
- No source Food/Recipe mutation that rewrites or clears historical Daily Log Complete state.
- No target-change coupling to Complete.
- No backup/restore or one-time-transfer propagation of Complete; E4-15 owns those semantics.
- No synchronization, background repair, compensating cleanup job, fallback, dual-write, or mixed authority.

## Background

E4-01 introduced positive date-owned Complete persistence and E4-02 exposed deterministic mark-Complete mutation/reconciliation. At the E4-03 baseline, remote Daily Log create/update/delete already own their commit/rollback boundary in `LogService`; update and delete use deterministic receipts within that transaction. Local Daily Log mutations already run through the repository's exclusive SQLite write coordinator. E4-03 inserts invalidation into those established transaction boundaries rather than invoking Complete cleanup afterward.

The accepted Epic 4 semantics are intentionally based on the stored historical nutrition result, not on whether an amount/serving input field changed. A nutrition-edit request that regenerates an exactly equivalent persisted snapshot set preserves Complete; a request that changes any authoritative stored nutrient snapshot clears it. Date moves are independently invalidating and clear both dates even if the nutrient snapshot itself is unchanged.

## Decisions and assumptions

- Complete invalidation is a mutation-side invariant, not a UI effect or cache-only behavior.
- Absence remains the only persisted not-confirmed-Complete state; invalidation deletes the positive date-owned assertion rather than writing a false row.
- Create and delete always change logged nutrition for their date and therefore invalidate an existing Complete assertion.
- A date move invalidates both source and destination regardless of nutrient snapshot equality because each date's logging coverage changed.
- Note and meal metadata do not alter historical nutrition and therefore preserve Complete when the date is unchanged.
- For a nutrition edit, exact persisted snapshot equivalence is the sole preservation criterion. Input equality is insufficient, and differing inputs may still preserve Complete if the authoritative persisted snapshot generation is exactly unchanged.
- Source Food/Recipe edits and target changes are outside the Daily Log mutation transaction and must not be coupled to Complete invalidation.
- Remote same-date serialization must compose with E4-02's existing first-Log date lock rather than creating a second date-lock authority.
- Local authority already serializes writes through one exclusive SQLite coordinator; invalidation must run inside that transaction instead of opening another one.
