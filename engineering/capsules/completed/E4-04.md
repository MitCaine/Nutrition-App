# E4-04 — Add the bounded Daily Logs History range contract

## Goal

Add one bounded, authority-scoped History range read to the existing Daily Logs capability so local SQLite and remote FastAPI/PostgreSQL return equivalent per-date historical nutrition evidence for inclusive ranges of at most 30 calendar dates.

## Outcome

`DailyLogsRuntime` exposes one `getHistoryRange(startDate, endDate)`-equivalent read. The selected authority returns one record for every requested calendar date, Complete state, first-logged-date metadata, and exact canonical nutrient evidence sufficient for E4-05 to calculate History projections without re-reading Logs or inventing zero values. Remote authority uses one HTTP request. Local authority reads SQLite directly. No History authority, UI, projection/average layer, target reconstruction, fallback, or synchronization is added.

## Non-goals

- No History route, charts, paging UI, cache/invalidation policy, or denominator calculations; E4-05/E4-06/E4-09+ own those layers.
- No 90-day/custom/unbounded request support or Today-inclusive History.
- No current/historical Target data or per-entry Food/Recipe graph payload in the range response.
- No migration, schema change, new runtime capability, synchronization, fallback, dual read, shadow read, or mixed-authority assembly.
- No change to Complete mutation/invalidation semantics from E4-01 through E4-03-C1.

## Background

Epic 4 defines History as a read projection over immutable Daily Log nutrient snapshots. The range read avoids 7 or 30 independent remote date reads and establishes one semantic evidence boundary for both authorities.

The existing `DailySummary` shape is not sufficient by itself because it does not retain explicit-zero provenance or whether any numeric evidence exists. E4-04 therefore preserves those distinctions directly so E4-05 never reconstructs unknown as zero or guesses provenance from displayed totals.

## Authority and precedence

1. `docs/project/version-1.2/epic-4/feature-prd.md` owns user-visible History scope and unknown-versus-zero behavior.
2. `docs/project/version-1.2/epic-4/data-contracts.md` owns the normative range request/response, exact evidence, first-logged-date, and selected-authority semantics.
3. `docs/project/version-1.2/epic-4/architecture-review.md` owns the approved bounded Daily Logs read boundary and prohibits a ninth authority/capability.
4. `docs/project/version-1.2/epic-4/implementation-backlog.md`, E4-04, and GitHub #117 own this delivery decomposition.
5. Existing Daily Log immutable snapshot, exact-value, calendar authority, Complete persistence, and owner-isolation contracts remain authoritative.

Mobile/runtime ownership is limited to Daily Log API/runtime types, the single remote transport call, the existing `DailyLogsRuntime`, direct local SQLite implementation, narrow error mapping, focused parity/delegation tests, and one shared fixture under `packages/shared-contracts/e4-04/`.

## Allowed changes

- Add one authenticated bounded GET operation equivalent to `/logs/history-range?start_date=...&end_date=...` under the existing Daily Logs API.
- Extend `DailyLogsRuntime` with exactly one History range read; do not add `HistoryRuntime` or a ninth capability.
- Accept canonical inclusive LocalDate endpoints with `startDate <= endDate`, cardinality 1–30 calendar dates, and `endDate <= yesterday` under authoritative calendar state.
- Add stable semantic error classifications equivalent to `history_range_date_invalid`, `history_range_order_invalid`, `history_range_too_large`, `history_range_future_endpoint`, and the existing authoritative-time-zone-required error.
- Return `startDate`, `endDate`, authority-global `firstLoggedDate | null`, and exactly one ascending day record for every requested date.
- For each day, return `hasLogs`, authoritative `isComplete`, and nutrient evidence with exact `amountKnown`, `amountEstimated`, canonical unit, `hasNumericEvidence`, `isExplicitZeroTotal`, unknown-contributor flag, and unknown-contributor count.
- Preserve explicit no-Log gaps as `hasLogs=false`, `isComplete=false`, and no nutrient evidence rather than numerical zero.
- Treat `known`, `estimated`, and explicit `zero` snapshots as numeric evidence; unknown-only evidence remains numerically unusable. `isExplicitZeroTotal` is true only when every numeric contributor is persisted with explicit `zero` status; a known or estimated amount numerically equal to zero is not relabeled explicit zero.
- Reuse immutable Daily Log snapshots and existing canonical aggregation/unit conversion. Parent nutrients are not synthesized from children and display rounding is not applied.
- Remote implementation may perform a small bounded set of owner-scoped SQL reads inside one HTTP operation for range snapshots, Complete rows, and earliest Log metadata; it must not fan out through per-date HTTP reads.
- Local implementation may perform direct bounded SQLite reads under existing ordered-read coordination and may refactor private aggregation helpers to share canonical semantics with `getDailySummary()`.
- Add/update focused tests and the shared parity fixture needed to prove local/remote semantic equality and one-request remote delegation.

## Forbidden changes

- No migration, schema/table/model change, Complete mutation redesign, mutation receipt change, or historical snapshot rewrite.
- No History UI, charts, range navigation, denominator/average calculation, projection layer, cache/stale-response work, or target-history reconstruction.
- No 90-day/custom/unbounded endpoint.
- No current Food/Recipe recalculation, parent-from-child nutrient manufacturing, or per-entry Food graph payload.
- No new runtime capability, fallback, local/remote mixed range, dual/shadow read, synchronization, background replication, or shared persistent History authority/cache.
- Do not modify frozen Epic 4 PRD/data-contract/architecture documents for implementation convenience.

## Decisions and assumptions

- E4-04 is an evidence-read task; E4-05 owns averages, denominator modes, chart points, coverage counts, and all projection math.
- The endpoint accepts any valid inclusive range of 1–30 dates even though initial UI modes are only 7 and 30 days; 1-day qualification is required by #117.
- A logged date with an absent nutrient does not get a synthesized unknown record; absence differs from an explicit unknown snapshot.
- Exact-zero numeric value and explicit-zero provenance are separate. Unknown-only nutrient evidence may serialize zero aggregate components for compatibility but must set `hasNumericEvidence=false`.
- `firstLoggedDate` is authority-global metadata, not limited to the requested interval.
- One remote request means one HTTP operation, not one SQL statement.
