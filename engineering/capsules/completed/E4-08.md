# E4-08 — Consolidate Daily Nutrition into one exhaustive one-day surface

## Goal

Replace the deferred Daily Nutrition destination with one exhaustive selected-day nutrient surface that combines consumed amount and target/reference context without recreating separate full-catalog Totals and Target Progress blocks.

## Outcome

`View Nutrition` from Daily Log opens Daily Nutrition for exactly the selected date. The screen presents the canonical nutrient hierarchy in collapsible sections, renders one row per visible nutrient using existing target/comparison semantics, exposes Nutrition targets as a secondary action, and returns to the same Daily Log date.

## Non-goals

- No multi-day History calculations, charts, range controls, denominator controls, or nutrient drill-down; E4-09 owns History.
- No Previous Day / Next Day controls inside Daily Nutrition.
- No redesign of target authority, tracking mode, DRI, Daily Value, or direction semantics.
- No new backend endpoint or response contract.
- No persistence migration or stored UI-preference model.
- No new runtime capability, synchronization, fallback, or authority mixing.
- No dedicated data-quality diagnostic surface.
- No fourth bottom-navigation tab.

## Background

E4-07 is integrated and archived. Daily Log now owns a `View Nutrition` action and the `daily-log-nutrition` route already carries the selected Daily Log date and restores that date when returning.

The current destination is only `DeferredDailyLogSurface`. Existing `DailyTargetComparison` evidence already contains consumed amount, target amount, percentage, authority, direction, tracking mode, status, and unknown-contributor state. Existing canonical nutrient helpers already own section grouping, display order, parent hierarchy, and visible indentation depth.

The former `TargetProgressSection` demonstrates the current target semantics but includes progress tracks, warning treatment, and explanatory suffixes that E4-08 must not copy wholesale.

## Authority and precedence

1. GitHub #121 owns E4-08 implementation scope and acceptance.
2. The frozen Epic 4 implementation backlog owns decomposition and sequencing.
3. `feature-prd.md` and `data-contracts.md` own product and target semantics.
4. E4-07 owns the Daily-Log-to-Daily-Nutrition navigation seam and selected-date context.
5. Existing target comparison contracts remain authoritative for target/reference semantics.
6. Existing canonical nutrient catalog/section helpers remain authoritative for grouping and hierarchy.
7. `NutritionRuntime` remains the sole application-data authority boundary.

## Allowed changes

- Replace the Daily Nutrition `DeferredDailyLogSurface` with a real `DailyNutritionScreen`.
- Reuse `useDailyTargetComparison(date)` as the existing combined selected-day consumed/target/reference projection.
- Reuse the existing Daily Log read/cache only as needed to distinguish unavailable intake from confirmed selected-date evidence.
- Reuse `groupCanonicalNutrientsBySection`, `canonicalNutrientParentId`, and `nutrientVisibleDepth`.
- Reuse existing target amount, percentage, authority, and direction formatting helpers.
- Add a pure presentation helper that maps comparison rows into E4-08 display semantics without creating another authority.
- Hold collapsed-section state only in `AppNavigator` memory so it survives route navigation during the current app session and resets when the app/navigator is freshly mounted.
- Extend the existing Nutrition targets route metadata narrowly so Back can return to the same Daily Nutrition date.
- Update bounded navigation/render tests affected by replacing the deferred surface.

## Forbidden changes

- No backend code, endpoint, schema, model, service, or migration.
- No mobile runtime or SQLite changes.
- No new target API or Daily Log API contract.
- No History implementation.
- No persistence of section collapse state to AsyncStorage, SQLite, server state, or recovery state.
- No independent date picker or Previous/Next controls inside Daily Nutrition.
- No new bottom tab.
- No progress-success/failure semantics for limit rows.
- No routine visible `Incomplete data`, unknown-contributor count, or warning suffix.
- No separate exhaustive Totals block beside an exhaustive Target Progress block.
- No unrelated cleanup.
