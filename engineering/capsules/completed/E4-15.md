# E4-15 — Extend backup/restore and one-time transfer for Complete state

## Goal

Preserve authoritative date-owned Daily Log Complete metadata across the two already-supported durability boundaries: coherent local SQLite backup/restore and the one-time PostgreSQL-to-SQLite personal transfer.

## Outcome

Current local backups validate and preserve explicit Complete assertions with their exact LocalDate and `completed_at` evidence. The one-time remote-to-local transfer advances to a new versioned contract that carries explicit owner-scoped Complete rows into the existing local Complete table. Historical transfer versions remain readable and imply no Complete assertions because they never carried that state.

## Non-goals

- No cloud backup service.
- No multi-device synchronization.
- No continuous replication.
- No merge semantics.
- No cross-authority reconciliation.
- No fallback or dual-write behavior.
- No inference of Complete from the existence, count, age, or content of Daily Logs.
- No change to Complete assertion or automatic invalidation behavior.
- No new Complete persistence table.
- No Daily Log nutrient snapshot rewrite or recalculation.
- No new backup UI.
- No general-purpose backup migration framework.
- No E4-16 parity matrix or broad physical-qualification closure work.

## Background

E4-01 introduced equivalent positive date-owned Complete persistence in remote PostgreSQL and local SQLite. Remote rows are keyed by `user_id + logged_date` and retain `completed_at`; local rows are keyed by `logged_date` and retain `completed_at`.

E4-01 deliberately kept Complete outside the E2-15 one-time transfer contract. The local transfer importer currently treats `daily_log_day_completions` as a runtime-only target-schema extension so historical transfer packages can still import into the newer SQLite runtime without creating or inferring Complete rows. E4-15 now owns propagation.

Local backup/restore is different from the one-time transfer. It already copies the entire SQLite database coherently. Therefore the Complete table is already physically present in current-schema backup bytes. E4-15 must strengthen validation and qualification around that state rather than inventing a second backup serialization path.

The local restore validator intentionally accepts only the exact currently supported SQLite schema. The Epic 4 requirement that older backups without Complete remain valid only where schema migration policy supports them does not authorize silently broadening that policy. Unsupported old backup schemas remain fail-closed. Historical one-time transfer formats remain supported through their explicit version contracts and produce no Complete assertions.

The existing current E2-15 transfer format is version 2 and is fixed to PostgreSQL revision `0027_serving_reference_measurement`. Since then, application revisions 0028 through 0031 changed source identity indexing, the canonical nutrient catalog, and finally added Complete persistence. Extending the current transfer therefore requires a new version rather than reinterpreting existing v2 bytes.
