# Capsule creator

**Historical compatibility only.** Unselected for new author-and-reviewer work.
Use this resource only for an existing pinned contract or an explicit retained
compatibility assignment. It does not create a new required stage. Current work
uses the project's adopted issue procedure and fresh independent review.


Read the [selected common contract](references/project-procedure.md), original issue,
required decisions/specifications, supplied source/runtime evidence and applicable
project constraints. An initial creator does not require a future capsule. The
controller owns intake, branch, instruction selection and authority; do not repeat
its orientation, recruit workers or implement product source.

Use supplied authenticated discovery and complete applicable task-directed
Tree-sitter navigation on supported source before returning the capsule. Reuse
unchanged relevant outputs rather than blindly repeat identical discovery. Inspect
returned locations, owning symbols, callers, interfaces, tests and contracts directly.
Retain actual invocation/directory, source and parser/runtime identity, coverage,
locations and gaps; carry relevant generated pointers/projection into the task.
Lexical call candidates are not resolved edges; import/help/link checks are not
source analysis. Documentation needs no parse. A required unavailable operation
needs controller-visible owner disposition, never silent parser/runtime substitution.

Produce one self-contained accepted-task draft using six headings: Objective;
Source and scope; Acceptance; Checks; Prerequisites; Handoff and closeout.
Objective identifies original requirements. Source and scope identifies exact base,
branch, authorized edits and affected docs, with concise original-outcome-keyed
implementation steps and consequential dependencies. Acceptance preserves each
original criterion/ID once. Checks links each original outcome and step to individually
identified proof cases: preconditions/setup, action/fault, independently expected
observation, plausible wrong behavior/control, literal commands/environment,
required artifacts/measurements, applicable routes, due phase and future owner.
Select targeted development/correction checks and risk-justified acceptance gates
up front, including relevant input bindings and expensive-suite runtime budgets.
Prerequisites names unresolved decisions/dependencies and genuine installed proof.
Handoff names actors/actions, return route and closeout obligations under project
controls. Correct affected current docs/examples/links or explain why unaffected.

Expose relationships sharing interfaces, transitions, dependencies or fixtures;
these inform coherent implementation groups without prescribing rigid groups.
Engineering work and proof must be jointly executable from the starting source or
explicitly authorized setup, without circular prerequisites. Separate implementation
route from the routes the finished capability must prove. Commands/checkboxes alone
are not discriminating proof. Keep historical compatibility expectations distinct.

Return consequential design/product/proof-plan gaps to the controller before
acceptance, never turn them into implicit implementor choices. The controller
substantively checks fidelity, completeness and joint feasibility against originals.
Return the draft, relevant source evidence and unresolved obligations through the
assigned route. Publish capsule-only only when explicitly granted; never grant
implementation readiness or independent candidate acceptance. Conditional format
reference: the selected controller procedure's Capsule format section governs
project extensions; it is not additional general worker orientation.
