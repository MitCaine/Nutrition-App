## Bounded controller readiness and setup

For a normal fresh attachment, the production route is `task evidence <issue> attach`, `readiness`, `setup`, `preflight`, then `review` after normal qualification, sealing and verification. These actions run under the existing controller state lock and authenticate the current task authorization, exact source and attachment. Existing stopped phases, pre-review failures, review results or setup authority block readiness/setup. The exact currently supported setup selection is codex-cli 0.159.2, gpt-6.1-sol and low effort. This proposal does not qualify that selection for operational protected review.

`readiness` requires the attachment existing private review key, explicit runtime path/SHA/version, model/effort, local workflow repository/full commit/manifest and a new `--account-readiness` output directly inside the controller state directory. `--account-routing-override` selects the inspected OpenAI route constraint (NO_CONSTRAINT, us or us_cr); origin remains https://chatgpt.com. The helper makes initialize/initialized and two read-only account/read requests with refreshToken=false, no thread or turn. It requires equal keyed account witnesses, authenticates the runtime again, and audits every observed event after bounded shutdown. Only one matching connection-scoped account snapshot is accepted; unknown/unsafe events and account changes fail. Raw identity is redacted before trace storage. Failure records a sticky STOP_REPLAN and diagnostics; no readiness or authority is minted. Success writes a candidate/authorization/epoch/instruction/runtime/model/account-bound readiness record and emits `owner_setup_request`, which contains the exact bounded grant proposed for owner inspection. Observation is not transmission approval.

The actual repository trusted owner must approve that exact request in one issue comment, using marker `<!-- nutrition-review-setup:v1 -->` and exactly one JSON fence containing the emitted request. It binds the current authorization identity, issue, candidate, binding, zero failure epoch, unique readiness attempt, complete instruction manifest, runtime, model/effort, readiness digest, keyed account identity, route, destination, launch_limit=1 and retries=0. Unknown or duplicate fields, wrong owner/repository/issue, stale source/epoch, changed bytes and anonymous local JSON cannot grant permission. The controller never posts this comment automatically.

`setup` accepts that owner comment ID through `--comment-id`, the existing readiness file, the same selection/instruction flags and new local `--account-route-approval` and `--owner-authority-provenance` output paths directly inside the controller state directory. Those two outputs must be distinct and absent. The controller retrieves the live owner comment twice through its existing authenticated GitHub transport, compares the exact request and body hash, rechecks current task authorization, runtime and source, and generates approval/provenance from the authenticated comment. It then atomically records review_setup_authority with the complete setup identity, owner comment ID/hash, current authorization identity and launches_used=0. Local files alone cannot manufacture this record. Partial output files from a failed setup are evidence and do not confer a dispatch grant; no automatic retry or overwrite occurs.

Preflight and review reauthenticate the live owner comment and current authorization; review consumes the single launch before invoking the helper. Post-review controller import rechecks the live owner authorization/comment before consuming the captured report; changed authority records a stop and preserves the unimported report. Existing helper account-before/after, pinned instruction delivery, effective readOnly network-disabled session checks, source/Git callbacks, report/trace bounds and receipt authentication remain mandatory. No report import action is added: the existing observed review handler captures the signed complete report and updates controller state.

Source corrections preserve the prior attachment in evidence_history and replace it without readiness, preflight or setup authority. A fresh candidate requires a new readiness observation and owner comment; old grants and consumed allowances never carry through correction. Installing this adapter first still requires a distinct trusted-introduction owner decision because the incumbent adapter only accepts 0.153.4. No bootstrap exception is inherited. The disposable protocol rehearsal is fixture proof only, with no model service, real App qualification or protected model reviewer approval. Actual final-environment launcher/nested sandbox, catalog/account route and protected review/report/terminal/controller proof remain separate operational obligations.
