# Dependency security repair research: #454 and #455

Research snapshot: 2026-10-30 local date (GitHub events extend into 2026-10-31 UTC). Inspected Nutrition base: `1fe53c37b1f2f7f90913b8bdf1f0d37e8ef2797d`. Research only; no dependency, install, runtime, Git, publication or alert-disposition change. PostCSS remains **8.5.30**.

## Decision supported by the research

The smallest plausible behavior repair is a separately maintained backport to deepmerge4.3.1, glob13.0.6 and minimatch10.2.6, with immutable provenance and tests against the actual packaged entrypoints. This is a candidate design, not a supported upstream release or a qualified implementation. No safe blanket cross-major override is established. Minimatch3 requires a separate advisory applicability decision: its inspected algorithm lacks the reported optimization mechanism, but the advisory still includes it. Do not manufacture a version number outside the affected range or close the alert on that basis.

The original issues require supported owner upgrades/replacements or separately assessed remediation, reject incompatible overrides/downgrades and require qualification and independent review. They remain open: [#454](https://github.com/MitCaine/Nutrition-App/issues/454), [#455](https://github.com/MitCaine/Nutrition-App/issues/455).

## #454: deepmerge

[GHSA-gcqx-w48m-w2h4](https://github.com/advisories/GHSA-gcqx-w48m-w2h4) lists4.2.0 through4.3.1 and no patched version. It concerns properties inherited by the returned object, not proof of global `Object.prototype` modification. [PR274](https://github.com/TehShrike/deepmerge/pull/274) is closed and unmerged; it is a proposed repair, not upstream support.

The proposed commit is `c5ad573121574db1c625b0aabcc6114ed7df6c5a`. Its [actual diff](https://github.com/TehShrike/deepmerge/pull/274/files) adds a key predicate rejecting `__proto__`, applies it to the target-copy loop and the source-merge loop, and preserves the existing inherited/non-enumerable-property check. Four tests cover null-prototype targets, nested null placeholders, target-owned special keys and cloned array elements. This is narrower than replacing the merging library, but deliberately changes treatment of that key. Custom merge/clone options still need regression coverage.

Installed `deepmerge/package.json` points to `dist/cjs.js`; inspecting it confirms the vulnerable copy/merge loops. Editing only upstream `index.js` would not repair the entrypoint used by Expo/Jest. A maintained package must include corrected CJS and UMD distributions, preserve exports/types/options and demonstrate that source and generated runtime agree. The installed MIT license is `deepmerge/license.txt`; retain its notice, upstream identity, proposed-patch author/commit and exact resulting artifact hash.

The prior external assessment found real Expo configuration and Jest preset/global merge callers. Those are build/developer inputs; no complete attacker-input control proof was supplied. Absence of direct app imports is insufficient for nonreachability. A future bounded regression should exercise the four upstream cases plus ordinary nested merges, arrays, symbols and supplied options through the packaged entrypoint and both owner callers. No such test ran in this research.

## #455: glob cancellation

[The advisory](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4) includes9.0.0 through14.0.1 and fixes14.0.2. Thus installed glob7.2.3 is outside this particular cancellation advisory. The relevant installed copy is13.0.6, whose upstream source identity is `e80cb38ae60d6cbff9e75f39032a994858994d35` in the advisory.

The complete fix is commit [`4682e8c9babee1b385202ede36389634e12076d7`](https://github.com/isaacs/node-glob/commit/4682e8c9babee1b385202ede36389634e12076d7), followed by version-only release commit [`93957bfedf11019063804027a7a5ad40d64cbe4f`](https://github.com/isaacs/node-glob/commit/93957bfedf11019063804027a7a5ad40d64cbe4f). The GitHub connector's compare confirmed exactly these two commits between14.0.1 and14.0.2.

Crucially, the repair has **five runtime edits**, not just the four changes described in the advisory: four aborted walker branches return immediately after invoking the callback; `onResume()` also loses its early aborted-signal return. Carrying only four branches would not reproduce the upstream repair. Tagged `src/walker.ts` blob identities are `a675fee2f5f964ee13c5efde2942094267417590` before and `34f076653684c3c2bc64c2ddc9ceeb8ca340a7a9` after. The13.0.6 source blob is `495e0a700e3c8a603ab2ba58a23b7c7be16015ee` and has corresponding sites. These are Git blob identities, not package integrity hashes.

Upstream added [signal tests](https://github.com/isaacs/node-glob/blob/4682e8c9babee1b385202ede36389634e12076d7/test/signal.ts) for no further reads following cancellation (async and synchronous stream), and a [stream regression](https://github.com/isaacs/node-glob/blob/4682e8c9babee1b385202ede36389634e12076d7/test/stream.ts) that pauses reads under backpressure then compares completion with synchronous traversal. Existing pre/mid-abort cases span async, sync, stream and sync-stream interfaces. Read those tests; none were executed here. A backport should retain all five runtime edits and translate tests to13's API without importing unrelated14 changes, then test both CJS/ESM artifacts, timeout rejection, post-rejection I/O, first-result cancellation and paused-stream completion under an external deadline.

The earlier assessment identifies an actual Expo TypeScript prerequisite caller using `AbortSignal.timeout(5000)` and another helper aborting after its first match. Cancellation correctness therefore matters to a real selected tool path. This does not establish remote application exploitability or complete attacker control.

## #455: minimatch modern and legacy lines

[The advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249) broadly lists versions below11.0.1. The described mechanism is generated glob-part amplification in optimization level2, followed by pairwise preprocessing.

The exact fix is [`77a0f5c4b80bdc641c3c930a1d9edf5ad2db57f8`](https://github.com/isaacs/minimatch/commit/77a0f5c4b80bdc641c3c930a1d9edf5ad2db57f8), parent `6f9f13168f7172d2ef824eef6c3a47e1517ae94a`. The inspected [source](https://github.com/isaacs/minimatch/blob/77a0f5c4b80bdc641c3c930a1d9edf5ad2db57f8/src/index.ts) bounds generated entries with the existing `braceExpandMax` option (default100,000), and skips pairwise deduplication above1,000 entries. It changes the optimizer, not merely input validation. Installed10.2.6 already has `braceExpandMax` for brace expansion and the same two vulnerable preprocessing functions, so an algorithm-level backport is plausible without replacing its matching engine. Equivalence and performance still require proof.

The upstream [regression tests](https://github.com/isaacs/minimatch/blob/77a0f5c4b80bdc641c3c930a1d9edf5ad2db57f8/test/preprocess-limits.ts) check configured and default expansion caps, ordinary below-cap matching, and large-set deduplication bypass with positive/negative matches. Do not execute the high-expansion cases against an unpatched dependency in the app process. Start with static assertions and small isolated bounded cases; reserve larger patched-only cases for an explicitly resource-bounded test process. A finite100,000-entry cap is not proof of acceptable latency on every platform.

**Legacy distinction:** the four installed3.1.5 copies have the same manifest identity. Direct inspection of `jest-config/node_modules/minimatch/minimatch.js` shows `make()` brace-expanding, splitting on slashes and directly mapping `parse()`. Searches of that complete file find no `optimizationLevel`, `firstPhasePreProcess` or `secondPhasePreProcess`; the new amplification algorithm is absent. This supports absence of this specific mechanism in that inspected implementation. It does not prove absence of every possible denial of service, alter the published affected range or justify calling3.1.5 scanner-clean. Obtain upstream advisory clarification or an explicit documented applicability disposition; keep the issue open while this remains unresolved. Do not transplant modern optimizer code into3 merely to claim a patch.

## Why blanket modern overrides are higher risk

The [glob14 changelog](https://github.com/isaacs/node-glob/blob/v14.0.2/changelog.md) documents adoption of minimatch11 and a different matcher engine, removed debug option, changes to walker result shapes and internal exported contracts, and ignore/Windows path semantics. It also records the much larger7-to9 rewrite: callback-to-Promise API, changed exports/classes/options and traversal semantics. Consequently replacing glob7 globally with14 is not a compatible security patch.

Installed minimatch3 exports a callable CommonJS function; [minimatch11 package exports](https://github.com/isaacs/minimatch/blob/v11.0.1/package.json) select ESM/CJS modules, and its source exports named bindings. Eleven also introduces `@isaacs/nonrecursive-glob-match` and brace-expansion5. A blanket3-to11 override changes API, engine and dependencies. Even10-to11 requires caller/result-shape review. The existing issue/assessment records compatible owner ranges still on affected lines, including newer inspected Expo/Jest owners; upgrading owners cannot be assumed to remediate these advisories without a fresh resolved graph. No Expo/RN/Jest migration is qualified here.

## Recommended delivery and ordered implementation

**Recommendation:** request a bounded, repository-maintained security-backport exception, then implement #454 first and #455 second as separate reviewable changes. This is the lowest compatibility-risk candidate among the inspected options; it still requires implementation proof. Existing [remediation rules](../operations/dependency-risk-management.md#remediation-rules) prohibit vendoring or overrides merely to silence findings. The proposed exception must authorize actual behavior repairs, transparent scanner status and continuing patch maintenance, not relax those rules or accept the remaining risks.

1. **#454:** preserve deepmerge4.3.1's API and dependencies; carry the exact reviewed two-loop `__proto__` repair, source and distributed entrypoints, license and attribution. Qualify actual Expo configuration/plugin modifications and Jest globals merging, including the four upstream hostile shapes and ordinary arrays/symbols/custom options. A deepmerge-only change should neither refresh other package versions nor alter the existing Zod/UUID selections.
2. **#455:** on the resulting reviewed base, preserve glob13.0.6/minimatch10.2.6's APIs and dependency versions while backporting the complete cancellation repair and bounded optimizer repair respectively. Leave glob7 alone for this cancellation advisory. Do not transplant the modern optimizer into minimatch3: seek an authoritative affected-range correction, or keep its explicitly unresolved applicability in #455. A separate owner-supported migration may later remove legacy3, but is not a prerequisite for repairing the modern reachable paths. A source repair to modern packages cannot justify closing the whole issue while legacy applicability is unresolved.
3. Prefer reviewed, **repository-contained package tarballs**, selected by exact version-scoped npm overrides, over Git branches, external fork registries, local-directory symlinks or install-time mutation. Retain original upstream package names and versions, and distinguish the local patch through explicit provenance and artifact hashes; do not use a fabricated fixed upstream version to alter scanner results. This is a proposed selection, not an installed dependency change. npm documents root [overrides and file/tarball specifications](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/); the exact real graph and version-selector delivery still need qualification.
4. Each artifact must have retained upstream tarball/integrity, exact upstream source/patch commits, complete readable patch, license notices, reproducible build/repack recipe and frozen build inputs. Generate source, CJS/ESM/UMD distributions and source maps consistently as applicable; never repair only unused TypeScript/source while shipping vulnerable compiled entrypoints. Compare the final unpacked package against the upstream package: only declared security changes and truthful provenance metadata may differ. Verify all runtime exports, files and dependencies, not just a generated archive checksum. A second clean build must reproduce the artifact; no network-selected floating build dependencies.
5. Install the artifacts through the lock **before any Expo/Jest process starts**. Several repository updater/qualification routes use `npm ci --ignore-scripts`; a `postinstall` patch would therefore be bypassed. npm confirms that [`ignore-scripts` skips lifecycle hooks](https://docs.npmjs.com/cli/v11/commands/npm-ci/). A lock-selected tarball contains the corrected bytes at extraction and does not require those hooks. Apply assertions to both ordinary scripted and ignore-scripts installs.
6. Extend only the current exact override/risk-validation contract for the explicitly approved artifact identities, selectors, owner edges, entrypoint hashes and full installed closure. Preserve historical UUID/Zod readers and their evidence. Reject unexpected extra copies, a new owning version, missing artifacts, hash/patch drift, symlink substitution and a PostCSS version other than8.5.30. Connect the compatibility/security checks to the existing normal qualification routes, with focused negative tests proving drift fails closed. Avoid an advisory-specific parallel framework.

### Delivery experiment actually performed

The author used a two-package **synthetic fixture**, not a patched real dependency: Node26.11.0/npm11.20.0 resolved a root local-tarball override for a transitive dependency, generated a lock with SHA512 integrity, copied that project to another directory and completed offline `npm ci --ignore-scripts`. The installed child was a regular directory, its relative `file:vendor/child.tgz` resolution survived relocation, and its test install-script marker was absent. This supports npm delivery feasibility only; it proves neither the real lock graph nor security behavior, other npm versions, ordinary install hooks, CI platform behavior or native compatibility. Version-qualified override selectors remain to be tested with the real candidate.

The first fixture command failed because the normal npm cache was outside writable authority. Its log is retained. The second used a fresh private task cache and passed; no cache ownership/permissions were changed. Source and existing environments were untouched. Raw fixture requests/results, original failure and fixture packages remain in the existing external evidence area. No vulnerable-package resource-exhaustion test ran.

## Recovery and exit criteria

Retain the current main SHA/lock, original upstream packages, readable patches, resulting artifacts, build inputs, successful and failed logs, and each original checkpoint. Work in isolated task worktrees with their own caches; never edit the installed primary dependency tree to prototype a repair. Preserve active and parked runtimes, generated iOS recovery, original stopped attempts and prior security work. No broad clean, cache purge, global install, release/tag rewrite, device reset or data/database change is needed.

If a backport fails behavior, reproducibility or compatibility proof, preserve its exact failed candidate and return to the prior qualified graph; do not conceal failure with a major override. Before integration rollback is simply retaining main and abandoning no evidence. After integration use a reviewed, protected corrective/revert change with installed verification; never reset protected main or overwrite immutable release history. Do not automatically revert unrelated later work.
